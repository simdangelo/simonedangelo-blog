# Create a PostgreSQL table with a million rows (Lab)
To create a **PostgreSQL** table with a large number of rows, you can use a combination of Docker and the `generate_series` function. This process allows you to quickly set up a database and populate it with millions of rows for testing purposes.
## Step-by-Step Guide
Here's how to create a PostgreSQL table with a million rows:
1. **Run a PostgreSQL Docker Container**: Start a new PostgreSQL instance using Docker. This command sets the `POSTGRES_PASSWORD` and names the container `pg1`.
    ```bash
    docker run -e POSTGRES_PASSWORD=postgres -d --name pg1 postgres
    ```
2. **Access the Database Shell**: Connect to the running container and access the `psql` command-line tool.
    ```shell
    docker exec -it pg1 psql -U postgres
    ```
    You are now in the PostgreSQL shell, ready to execute commands.
3. **Create a Table**: Create a new table. In this example, the table is named `temp` and has a single column `t_value` of type `INTEGER`.
    ```sql
    CREATE TABLE temp (t_value INTEGER);
    ```
4. **Populate the Table with Data**: Use the `INSERT INTO` statement combined with the built-in `generate_series`function to populate the table. The `generate_series` function creates a sequence of numbers, which you can use in a `SELECT` statement.
    ```sql
    INSERT INTO temp (t_value)
    SELECT
        (random() * 100)::int
    FROM
        generate_series(0, 1000000);
    ```
    - `generate_series(0, 1000000)` produces a list of numbers from 0 to 1 million.
    - `random()` generates a random floating-point number between 0.0 and 1.0.
    - `random() * 100` scales the random number to be between 0 and 100.
    - `::int` casts the resulting float to an integer. This gives you a million random integer values to insert into the table.
## Verifying the Data
After the command finishes, you can verify that the table has been populated correctly:
- **View some rows**: `SELECT t_value FROM temp LIMIT 10;`
- **Count all rows**: `SELECT count(*) FROM temp;`

This method provides a quick and efficient way to create a large dataset for testing performance, indexing, and other database features. You can easily modify the `generate_series` function to create more rows or adjust the `random`function to create different types of data.

# Getting started with Indexing (Lab)
Indexing is a fundamental concept in database management that significantly improves query performance. An **index** is a data structure, often a B-tree, that provides a fast lookup mechanism to find data within a table without having to scan the entire dataset.
## What Is Indexing?
Think of an index like the index at the back of a book. Instead of reading the entire book to find a topic, you look up the topic in the index, which gives you the exact page number to jump to. In databases, an index works similarly by creating a sorted list of values from one or more columns that point to the physical location of the corresponding rows in the table. This allows the database to quickly locate data, drastically reducing query time, especially on large tables.
## The Impact of Indexing
The author demonstrates the impact of indexes using a **PostgreSQL** database with a large `employees` table containing 11 million rows. The `ID` column has a primary key, which automatically creates an index. The `name` column has no index initially.
### Queries with an Index
- **Query:** `SELECT ID FROM employees WHERE ID = 2000`
    - **Performance:** The database uses the existing index on the `ID` column. Since the `ID` is part of the index, **PostgreSQL** doesn't need to go to the main table to fetch the data. The query is extremely fast, taking only **0.6 milliseconds**.
- **Query:** `SELECT name FROM employees WHERE ID = 5000`
    - **Performance:** The database uses the index to find the row with `ID = 5000`. However, the `name` column is not in the index. The database has to perform an extra step to jump to the main table (the heap) to retrieve the `name` value. This is slower, taking around **2.5 milliseconds**. The author notes that even with this added step, this query is still very fast because the index reduces the search space.
## The Dangers of Missing Indexes
The author shows what happens when a query targets a column without an index.
- **Query:** `SELECT ID FROM employees WHERE name = 'xz'`
    - **Performance:** The database, realizing there is no index on the `name` column, resorts to a **full table scan** (or a **parallel sequential scan** in **PostgreSQL**). It has to read all 11 million rows to find the one matching the name. This query is extremely slow, taking about **3 seconds**, highlighting a massive performance difference.
## Creating and Using Indexes
To fix the slow query, the author creates an index on the `name` column: `CREATE INDEX employees_name ON employees (name)`.

After creating the index, the same query on the `name` column becomes much faster:
- **Query:** `SELECT ID FROM employees WHERE name = 'xz'`
    - **Performance:** The database now uses the new index, and the query time drops to **47 milliseconds**. While still slower than an ID lookup, it's a huge improvement from the original 3 seconds.

The author also highlights a common mistake with queries that prevent an index from being used.
- **Query:** `SELECT ID FROM employees WHERE name LIKE '%xz%'`
    - **Performance:** Despite the existence of an index on the `name` column, this query still performs a **full table scan**. The `LIKE` operator with a leading wildcard (`%`) is an "expression," not a literal value, which a standard B-tree index cannot effectively search. This forces the database to scan every row to check the condition. The author emphasizes that a full table scan can kill performance and should be avoided whenever possible.
## Conclusion
The author concludes by summarizing that while indexes are crucial for performance, they are not a magic solution. The database's query planner decides whether to use an index or not. As a developer, it's your responsibility to write queries that allow the database to use indexes effectively. The author also provides two key takeaways:
- **`SELECT *` is often a bad practice**, especially on tables with large data columns, because it forces the database to retrieve all data, which can be expensive.
- **Not all queries can use an index**, particularly those with expressions or functions on indexed columns. For example, a query like `WHERE name LIKE '%...%'` will ignore the index and result in a slow sequential scan.

# Understanding the SQL Query Planner and Optimizer with `EXPLAIN`
The `EXPLAIN` command in **PostgreSQL** is a tool used to understand how the database's query planner intends to execute an SQL statement. It provides a detailed plan and cost estimations without actually running the query, which helps developers identify and optimize performance bottlenecks.
## Understanding the `EXPLAIN` Output
An `EXPLAIN` output typically shows a hierarchical plan that should be read from the innermost operation outwards. Each step in the plan includes cost estimations and other metrics:
- **Query Plan:** This describes the operation the database will perform. A **sequential scan** means the database will read the entire table from beginning to end. An **index scan** means it will use an index to find the data, which is much faster
- **Cost:** The cost is shown as `(startup_cost..total_cost)`.
    - **`startup_cost`:** The estimated cost to get the first page. This can be zero if the database can immediately start fetching data (e.g., a sequential scan). It will be higher if the database has to do preliminary work like sorting or aggregation before it can return the first result.
    - **`total_cost`:** The estimated total cost to complete the entire operation.
- **Rows:** The estimated number of rows that the operation will return.
- **Width:** The estimated average size in bytes of the rows returned by the operation.

# Bitmap Index Scan vs Index Scan vs Table Scan
To efficiently retrieve data, a database's query planner chooses one of three primary scan methods: **sequential scan**, **index scan**, or **bitmap index scan**. The choice depends on the query's conditions and the availability of indexes, each with its own trade-offs in performance.
## Sequential (or Full Table) Scan
A **sequential scan** is the most basic method where the database reads every single row in the table from start to finish. It's the default choice when a query has no filter or when the filter is so broad that using an index would be more costly than simply reading the entire table. For example, a query like `SELECT * FROM grades` without a `WHERE` clause will always result in a sequential scan. Similarly, a query like `SELECT name FROM grades WHERE ID > 100` on a table with 5 million rows will likely trigger a sequential scan because most rows would match, making an index scan inefficient.
## Index Scan
![](Pasted%20image%2020250826213936.png)
An **index scan** uses a B-tree or a similar index to quickly find the specific rows that match a query's `WHERE` clause. It's the preferred method when the query's conditions are selective, meaning they narrow down the results to a small number of rows. The process involves two steps:
1. **Scanning the index:** The database navigates the index tree to find the row's location. This is very fast since the index is much smaller and more organized than the table.
2. **Fetching from the table (heap):** Once the index provides the location of a row, the database performs a random access read to go to the main table (the heap) and fetch the full row data.

This process is highly efficient for fetching a few rows, but becomes slow if the query returns a large number of rows. This is because each individual row fetched from the heap is a separate I/O operation, which can add up quickly and lead to a performance bottleneck known as "random I/O."

For example, the query `SELECT name FROM grades WHERE id < 100` has this result:

In this case, for each value that it finds, it finds the page where that row exists and goes back to the heap to pull that page, which kind of have one or more rows, and then pulls that value. And this is called random access. On the other hand, as we have already seen in the [Index Scan](#Index%20Scan) paragraph, when we asked for `id > 100`, Postgres is able to understand (by computing some statistics) that we'll fetch a lot of rows and it would be extremely expensive to do a random access, so it decides to do a sequential scan because in this case it's way cheaper:

## Bitmap Index Scan *(It's not so clear in my opinion)*
A **bitmap index scan** is an intelligent compromise between a sequential scan and an index scan, primarily used by **PostgreSQL**. It is ideal for queries that are somewhat selective but not selective enough for a standard index scan to be efficient. The process involves three steps:
1. **Creating a bitmap:** The database scans one or more indexes that match the query's `WHERE` conditions. Instead of fetching rows one by one, it creates a **bitmap**, which is an in-memory array of bits. Each bit corresponds to a data block (or page) in the main table. When the index scan finds a matching row, it sets the corresponding bit for that data block to 1.
2. **Combining bitmaps (optional):** For queries with multiple conditions joined by `AND` or `OR` (e.g., `WHERE g > 95 AND ID < 10000`), the database can create a bitmap for each condition and then perform a logical `AND` or `OR` operation on them. This quickly identifies the data blocks that satisfy all conditions.
3. **Fetching in bulk (Bitmap Heap Scan):** Finally, the database uses the completed bitmap to perform a single, efficient, bulk read of all the required data blocks from the heap. This minimizes the number of random I/O operations. After fetching the data blocks, a **recheck** may be performed to filter out any rows that were included by chance (e.g., a page containing multiple rows, only some of which satisfy the condition).

This method is particularly effective for queries that combine multiple indexed columns, as it can leverage all available indexes to build a highly optimized fetch list before reading the actual data.

# Key vs Non-Key Column Database Indexing
An index can contain two types of columns: **key columns** and **non-key columns**. A **key column** is the primary field on which the index is built, and it's used to efficiently search for and filter data. A **non-key column** is a secondary field that is included in the index to allow queries to retrieve data without having to visit the main table.
### The Problem with Standard Indexes
A standard index, also called a **key-only index**, stores only the values of the key column along with a pointer to the main table (or "heap") where the full row data is stored.
- When you execute a query like `SELECT ID, Grade FROM students WHERE Grade BETWEEN 80 AND 95`, the database first performs an **index scan** on the `Grade` key column. It efficiently finds all the rows that match the condition.
- However, because the `ID` column is not stored in this index, the database then has to perform a separate, costly operation to visit the main table for each matching row to retrieve the `ID`. This is known as **heap fetching** or random I/O and significantly slows down the query, especially when dealing with a large number of results.

In the example with a 50 million-row table and a standard index on `Grade`, a query selecting both `ID` and `Grade` takes about **16 seconds**. This is an improvement over the 21 seconds for a full table scan, but still far from optimal.
### The Solution: Non-Key Columns
Databases like **PostgreSQL** support including **non-key columns** in an index. These columns are not used for searching or sorting but are simply stored alongside the key columns. This capability allows the index to be used for **index-only scans**, which are the fastest type of query execution.
1. **Creating the Index:** An index is created on the `Grade` key column while including the `ID` as a non-key column. `CREATE INDEX students_grade_idx ON students (grade) INCLUDE (id);`
2. **Executing the Query:** When the same query `SELECT ID, Grade FROM students WHERE Grade BETWEEN 80 AND 95` is run, the database's query planner recognizes that both `ID` and `Grade` are available directly in the index.
3. **Index-Only Scan:** The database performs a single, efficient scan of the index without ever needing to touch the main table. This eliminates the random I/O caused by heap fetching and makes the query significantly faster. In the example, the query time drops to around **4 seconds** for the first run and even faster on subsequent runs due to caching.

The `EXPLAIN ANALYZE` output for this optimized query would show `Heap Fetches: 0`, confirming that the database never had to visit the main table. This is the ultimate goal for read-heavy queries:
![[Pasted image 20250915231511.png]]
### Trade-Offs
While non-key columns can dramatically boost read performance, they come with a few trade-offs:
- **Larger Index Size:** Including additional columns increases the size of the index. A larger index takes up more disk space and can be slower to build and update during write operations.
- **Reduced Cache Hit Rate:** A larger index might not fit entirely into the database's memory cache, forcing the system to read parts of the index from disk, which is slower than reading from memory.

# Index Scan vs Index Only Scan
An **index scan** and an **index-only scan** are both methods for retrieving data using an index, but they differ in whether they need to access the main table to complete the query.
### Index Scan
An **index scan** is a query execution plan where the database uses an index to locate the physical address of the data, but still needs to access the main table to retrieve the full row.
1. **Search the Index:** The database uses the index (e.g., a B-tree) to quickly find the key value specified in the `WHERE` clause. This is much faster than a sequential scan because it avoids searching the entire table.
2. **Fetch from the Heap:** Once the index returns the location of the matching row, the database must perform a separate disk read to go to the main table (also called the "heap") and retrieve the requested columns. This is required because the columns you want to select are not stored in the index itself.

For example, on a table with an index on `ID`, the query `SELECT name FROM grades WHERE ID = 7` performs an index scan. The database uses the index to find the row with `ID = 7` but must then go to the main table to fetch the `name` column, which is not part of the index. This can be less efficient because it involves two I/O operations: one for the index and one for the main table.
### Index-Only Scan
An **index-only scan** is a highly optimized query execution plan where the database can satisfy the query by reading only from the index, without needing to access the main table. This is possible if all the columns requested in the `SELECT` list are already present in the index.

There are two primary ways to achieve an index-only scan:
1. **Selecting an Indexed Column:** If a query only requests the column that the index is built on, the database can return the result directly from the index. For example, the query `SELECT ID FROM grades WHERE ID = 7` can be an index-only scan because the `ID` is the key column of the index, and its value is already stored there.
2. **Using Non-Key Columns:** To make this more useful, you can add **non-key columns** (also called "included" columns) to an index. This allows the index to store additional data that is not used for searching but can be returned in a query. By including frequently selected columns in an index, you can turn a regular index scan into a faster index-only scan. For example, if you create an index on `ID` and include `name` as a non-key column with `create index od_idx on grades(id) include (name)`, the query `SELECT name FROM grades WHERE ID = 7` will now perform an index-only scan because both pieces of information are available within the index structure.

# How Database Optimizers Decide to Use Indexes (Still to Watch!!)
When a query involves multiple columns with indexes, a database optimizer uses heuristics and statistics to choose the most efficient execution plan. It can use one or more of the available indexes or decide to perform a full table scan if that's deemed faster.
### The Optimizer's Decision-Making Process
The database optimizer is a component of the database management system that evaluates multiple query plans and selects the one with the lowest estimated cost. It relies on **statistics** about the table and its indexes, such as the number of rows, the distribution of values, and the density of data. These statistics are not always perfectly up-to-date, especially after large-scale data insertions, which can lead the optimizer to make a suboptimal choice.
### Querying with `AND` and `OR`
The choice of an `AND` or `OR` condition significantly impacts the optimizer's strategy.
- **For an `AND` query** (e.g., `WHERE F1 = 1 AND F2 = 4`): The optimizer knows the result set will be the intersection of the two conditions. It's looking for the most selective (i.e., narrowest) path.
- **For an `OR` query** (e.g., `WHERE F1 = 1 OR F2 = 4`): The optimizer knows the result set will be the union of the two conditions. It might fetch a large number of rows and must consider the cost of combining them.
### Optimizer Scenarios
#### Scenario 1: Using Both Indexes
The optimizer might decide to use a **bitmap index scan** on both `F1` and `F2`. It will:
1. Scan the `F1` index to find all matching row IDs.
2. Scan the `F2` index to find all matching row IDs.
3. Perform a logical `AND` (for intersection) or `OR` (for union) operation on the two sets of row IDs.
4. Access the main table once to fetch the final rows.

This method is efficient when both conditions are moderately selective and retrieving data from both indexes is cheaper than performing a full table scan or a single-index scan.
#### Scenario 2: Using One Index
The optimizer might decide to use only one of the indexes. This happens when one index is much more **selective** than the other. For instance, if the `F1` column is a primary key or has very few matching rows, the optimizer will use the `F1` index to find the rows quickly. It then proceeds to fetch those rows from the table and applies the second condition (`F2 = 4`) as a simple filter. This approach avoids the overhead of scanning the second index, which would be an unnecessary cost if the first index already narrows the results down to a very small set.
#### Scenario 3: Using No Index (Full Table Scan)
In some cases, the optimizer might decide that using any index is not worth the effort. This can happen when:
- The query is **not selective at all** (e.g., `WHERE F1 > 0`), and the condition matches a large percentage of the table's rows.
    
- The optimizer's statistics are outdated, leading it to mistakenly believe that an index scan would be more expensive than a sequential scan. This is a common problem after bulk inserts.
    

To prevent suboptimal plans due to outdated statistics, you can manually run database commands like **`ANALYZE`** (in PostgreSQL) or **`GATHER STATS`** (in Oracle) to update the table statistics. Additionally, if you know the optimizer is making a poor decision, you can use **query hints** to force it to use a specific index.
