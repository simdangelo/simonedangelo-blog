# How tables and indexes are stored on disk
In database systems, **tables** and **indexes** are stored on disk in a structured manner to optimize data retrieval and management. Understanding these concepts is crucial for grasping how databases perform.
## Storage Concepts
- **Row ID:** A unique identifier for each row in a table. Some databases, like Postgres, create a system-maintained Row ID, while others, like MySQL, use the primary key as the Row ID.
	![](Pasted%20image%2020250824183605.png)
- **Page:** The fundamental unit of disk storage for a database. A page is a fixed-size block of data, typically 8 KB in Postgres or 16 KB in MySQL, that can hold multiple rows. When a database needs to read data from disk, it always fetches at least one entire page, not individual rows. Assume each page holds 3 rows, with 1001 rows you will have 1001/3=~333 pages.
	![](Pasted%20image%2020250824183728.png)
- **I/O (Input/Output) Operation:** An **I/O operation** is the database's request to read data from or write data to disk. The goal of any database optimization is to minimize these operations. An I/O is a bulk operation that fetches one or more pages at a time, so it's a "get all or nothing" kind of deal. You can't just fetch a single column from a row; you get the entire page, and the database has to discard the parts you don't need. The operating system may use a cache to optimize I/Os, so a request to disk might not even hit the physical medium right away, but this can introduce risks.
- **Heap:** The **heap** is the part of the database where all the raw table data is stored. It's an unordered collection of pages, containing every row and column. Because it's not organized, finding a specific row requires the database to perform a **full table scan**, which means reading every single page until it finds the data it needs. This is a very expensive and slow operation.
	![](Pasted%20image%2020250824185802.png)
- **Index:** An index is a separate data structure that helps locate specific data within the heap quickly. It does not store the full row data but, instead, holds a copy of the indexed columns along with a **pointer** (the Row ID) to the exact location of the full row in the heap. An index is typically organized as a **B-tree**, which allows for efficient searches by navigating a tree structure.
## How a Query Works
- **Without an Index:** If you query a table without an index on the search column, the database must perform a **full table scan** of the heap. It will read every page on the disk, one by one, and examine each row until it finds the one that matches the search condition. This is a very slow process, especially for large tables.
	![](Pasted%20image%2020250824192904.png)
- **With an Index:** When a query uses an indexed column, the database first searches the index. This search is much faster because the index is a smaller, organized data structure (B-Tree guarantees great performance). Once the index finds the entry for the desired row, it uses the Row ID to jump directly to the correct page in the heap. It then performs a single I/O to fetch that specific page, which contains the full row data, and returns the result. This process is significantly more efficient. For example, suppose an index is created on `emp_id`:
	![](Pasted%20image%2020250824191648.png)
	+ The element `10 (1,0)` in Page 0 means that the employee with `emp_id=10` lives in row_id=1 and lives in Page 0.
	+ The element `110 (11,3)` in Page 1 means that the employee with `emp_id=110` lives in row_id=11 and lives in Page 3.
## Cluster Index
While a standard index is a separate data structure from the heap, a **cluster index** physically organizes the heap's data according to the index's sort order.
- **Organization:** This approach effectively makes the table data itself ordered, which is common for a primary key. For example, in MySQL's InnoDB engine, the primary key is a clustered index. This means all the table's rows are physically sorted on disk based on the primary key's value.
- **Performance Trade-offs:** This physical ordering makes queries on the primary key extremely fast. However, it can make writes very slow, especially when inserting a new row with a random key, such as a UUID. Since the UUID is not sequential, the database must find a random physical location on the disk to maintain the sort order, which leads to a "scattershot" of writes and can severely impact performance. In contrast, Postgres uses a secondary index for its primary key, where every index points to a system-maintained Row ID in the heap, which is less efficient for reads but handles random writes better.

# Row-based vs Column-based Databases
**Row-oriented** and **column-oriented** database storage are two distinct ways to physically store tables on disk. Each has unique strengths and weaknesses that make them suitable for different use cases.
## Row-Oriented Databases (Row Store)
In a row-oriented database, data is stored as a series of complete rows, one after the other. This model is very intuitive and is the default for most traditional relational databases like Postgres and MySQL. Here's an example:
![](Pasted%20image%2020250824212141.png)
![](Pasted%20image%2020250824212131.png)

Specs:
- **Physical Storage:** All data for a single row is stored together in a contiguous block. For example, the ID, first name, last name, and salary for a single employee are all physically grouped together. When a new row is added, it is simply appended to the end of the table.
- **I/O Operations:** When a query needs to read data, an I/O operation fetches an entire block, which contains one or more complete rows. This means that even if a query only asks for one column, it gets all the other columns in that block for free. This can lead to inefficient reads if the query only needs a small number of columns from a large table.
- - **Performance:** This storage style is highly efficient for workloads that deal with entire rows, such as **online transaction processing (OLTP)**.
    - **Writes:** Writing new data is fast because a new row can be quickly appended.
    - **Reads (Multi-Column):** Queries that need to retrieve all or many columns from a single row, like `SELECT * FROM Emp WHERE id=1`, are very fast because all the necessary data is already grouped together. Once a single block is read from disk, all the data for multiple rows and columns is already in memory, making subsequent reads for other columns from that block virtually free. Here's a visual explanation:
	    ![](Pasted%20image%2020250824220940.png)
- **Inefficiencies:** Row-oriented databases are not ideal for analytical workloads.
    - **Aggregation:** Queries that perform aggregate functions on a single column (e.g., `SELECT SUM(salary)`) are inefficient because the database must perform a full table scan. It has to read every single row, pulling all the columns in each row (even the unnecessary ones), just to get to the salary value. Here's a visual explanation:
	    ![](Pasted%20image%2020250824221148.png)
    - **Compression:** Compression is not very effective because each block contains a wide variety of mixed data types, making it difficult for algorithms to find patterns to compress.
## Column-Oriented Databases (Column Store)
IIn a column-oriented database, data is stored as a series of columns. This approach is common in data warehouses and systems designed for analytics. Here's the blocks of a column-based database:
![](Pasted%20image%2020250824215945.png)

Specs:
- **Physical Storage:** All the values for a single column are stored together in a contiguous block on disk. For example, all employee IDs are stored together, followed by all first names, then all last names, and so on. To link the values back to a specific row, a **Row ID** is stored with each value.
- **I/O Operations:** A query on a column-oriented database only reads the specific columns it needs. This means a query to find the sum of all salaries only reads the blocks for the salary column, ignoring all other data.
- **Performance:** This storage style is perfect for **online analytical processing (OLAP)**.
    - **Aggregation:** Aggregation is incredibly efficient because the database only has to read the relevant column, and all the data is located together. It can read millions of salaries with a minimal number of I/O operations. Here's a visual explanation:
	    ![](Pasted%20image%2020250824221058.png)
    - **Compression:** Compression is very effective because each block contains homogeneous data (e.g., all numbers or all strings), allowing for a high degree of data deduplication and compression.
- **Inefficiencies:** Column-oriented databases are not well-suited for transactional workloads.
    - **Writes:** Writing a new row is slow because it requires the database to update a separate physical location for each column's data. This "scattershot" of writes across the disk is very inefficient.
    - **Updates**: Inefficient for the same reasons of "writes".
    - **Reads (Multi-Column):** A `SELECT *` query is extremely inefficient because the database must perform a separate I/O operation for _each_ column to rebuild the row, leading to a huge number of disk seeks. Here's a visual explanation:
	    ![](Pasted%20image%2020250824220757.png)

## Summary of Pros and Cons
| Feature         | Row-Oriented                                | Column-Oriented                                    |
| --------------- | ------------------------------------------- | -------------------------------------------------- |
| **Use Case**    | OLTP (Transactions, lots of reads & writes) | OLAP (Analytics, lots of aggregations)             |
| **Writes**      | Fast and efficient                          | Slower, requires touching many blocks              |
| **Reads**       | Efficient for retrieving entire rows        | Efficient for single-column reads and aggregations |
| **`SELECT *`**  | Efficient                                   | Very inefficient                                   |
| **Aggregation** | Inefficient (reads entire rows)             | Highly efficient (reads only needed columns)       |
| **Compression** | Less effective                              | Highly effective (due to homogeneous data)         |

Ultimately, the choice between a row-oriented and column-oriented database depends on the application's workload. Many modern databases are **hybrid**, allowing for a mix of storage styles. For example, some databases allow a table to be stored as a column store while others use row-based storage, or they can even dynamically switch between the two.

# Primary Key vs Secondary Key
A **primary key** and a **secondary key** are both used in databases to uniquely identify records, but they differ fundamentally in how they organize and store data. Understanding these differences is crucial for optimizing database performance.
## Primary Keys
A primary key uniquely identifies each row in a table. It also acts as a **clustered index**, which means the database physically stores and organizes the data rows according to the primary key's value. This organization is called **clustering**.
### How Clustering Works
When a primary key is defined, the database maintains a strict order for the data. When you insert a new row, the database doesn't just append it to the end; it has to place it in the correct sorted position based on its primary key value. For example, if you insert the value '2' after '1' and '8' have already been inserted, the database will have to "make space" for the new row between '1' and '8'.

This constant reordering introduces an overhead or cost during data insertion and updates. However, it offers a significant advantage for data retrieval, particularly for **range queries** (e.g., "give me all values between 1 and 9"). Because the data is physically stored in a sorted manner, the database can retrieve all the requested rows in a single read operation, which is highly efficient.

> A clustered index that is sequential, such as an auto-incrementing integer, is highly efficient because new data is always appended to the end, minimizing the need for reordering.
### Primary Key Implementations
Different database systems handle primary keys differently:
- **MySQL**: By default, MySQL requires a primary key and organizes the table as a clustered index around it.
- **Oracle**: Oracle refers to this type of organization as an **Index-Organized Table (IOT)**.
- **SQL Server**: SQL Server calls this a **clustered index**.
## Secondary Keys
A secondary key, or a **secondary index**, is a separate data structure that points to the actual data rows. The data in the table itself is not physically organized by this key; it's stored in a **heap**, which is essentially an unordered collection of data.
### How Secondary Indexes Work
The secondary index is a separate, ordered structure (often a B-tree) that stores the key values and the location (or row ID) of the corresponding data in the heap. When you want to retrieve a record using a secondary key, the database must perform two steps:
1. **Search the index**: First, the database searches the secondary index to find the row ID of the data it needs.
2. **Access the heap**: Next, it uses the row ID to "jump" to the heap and retrieve the entire data row. This two-step process can be less efficient than a single lookup on a primary key because it involves an additional I/O operation.
### Secondary Key Implementations
- **PostgreSQL**: In PostgreSQL, all indexes, including those created for primary keys, are secondary indexes. The table itself remains an unordered heap.
- **Oracle**: An unordered table without a clustered index is called a **Heap-Organized Table (HOT)**.
