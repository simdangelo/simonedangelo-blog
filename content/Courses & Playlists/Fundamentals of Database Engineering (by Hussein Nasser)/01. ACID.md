# Introduction to ACID
ACID, which stands for **Atomicity**, **Consistency**, **Isolation**, and **Durability**, represents four fundamental properties of relational databases. An understanding of these principles is crucial for any engineer working with databases, including relational systems like Postgres, MySQL, SQL Server, and Oracle, as well as NoSQL and graph databases.
## Understanding the Core Concepts
Before diving into the ACID properties, it is essential to first grasp what a **database transaction** is. A transaction is a single unit of work that must be completed in its entirety or not at all.
## The Four Pillars of ACID
The video discusses each property in detail, explaining their importance. The speaker highlights that he will discuss **Atomicity** and **Isolation** before **Consistency** because he believes this order is crucial for a complete understanding.
- **Atomicity:** This is the first property to be discussed. It guarantees that all operations within a transaction are treated as a single, indivisible unit. The transaction either completes successfully or is entirely rolled back, leaving the database unchanged.
- **Isolation:** This property addresses concurrent transactions. It ensures that multiple transactions running at the same time do not interfere with each other. Each transaction's outcome is independent of others, preventing them from seeing intermediate, uncommitted changes made by other transactions.
- **Consistency:** The video emphasizes that understanding atomicity and isolation is key to understanding consistency. **Consistency ensures that a transaction takes the database from one valid state to another.** It prevents data corruption and ensures that the database remains in a consistent state even after multiple concurrent transactions. The speaker repeatedly mentions that a lack of isolation can lead to unexpected and bizarre data, highlighting the importance of this property.
- **Durability:** This is a critical property, often sacrificed by some NoSQL databases for performance. **Durability ensures that once a transaction has been successfully committed, its changes will persist permanently, even in the event of a system failure like a crash or power loss.** The data is saved to a non-volatile storage location.

# What is a Transaction?
A **database transaction** is a fundamental concept in database management. It is a collection of SQL queries that are treated as a single, indivisible unit of work. The main purpose of a transaction is to ensure that a series of operations either all succeed or all fail together, maintaining the database's integrity and consistency. This is especially important because a single logical action often requires multiple queries across different tables.
## Transaction Lifecycle and Operations
A transaction's life typically involves these key stages:
- **Begin:** A transaction starts with a `BEGIN` statement. This signals to the database that subsequent queries are part of a single unit.
- **Queries:** Within the transaction, multiple queries can be executed. These can include `SELECT`, `UPDATE`, `INSERT`, and `DELETE` statements. For example, to transfer $100 from account A to account B, the transaction would involve three queries:
    - A `SELECT` query to check if account A has enough money.
    - An `UPDATE` query to deduct $100 from account A's balance.
    - Another `UPDATE` query to add $100 to account B's balance.
- **Commit:** If all queries are successful and the user is satisfied, a `COMMIT` statement is issued. This permanently saves all the changes made during the transaction to the database's non-volatile storage (disk).
- **Rollback:** If something goes wrong—either due to a user command or a system crash—a `ROLLBACK` is issued. This command undoes all the changes made within the transaction, restoring the database to its state before the transaction began.

The video highlights a key difference in how databases handle these changes: some might write each change to disk as it happens, while others store changes in memory and write them all at once during a `COMMIT`. The first approach makes `COMMIT` faster but `ROLLBACK` slower, while the second makes `COMMIT` slower but `ROLLBACK` faster. This choice is an engineering trade-off made by database developers.
## Unexpected Endings
Transactions can end unexpectedly, such as when the database crashes. If a crash happens in the middle of a transaction, the database must know how to perform an automatic rollback when it restarts to prevent inconsistent data. Commits in Postgres are the fastest that you can get because they do that in a way such that any query executed during the transaction tries to persist this change. So Postgres does a lot of IO, but its commits are beautiful fast.

A crash during a `COMMIT` is especially risky, as it can be unclear whether the transaction was fully committed or not.

Different databases handle these situations differently based on their design choices and optimizations.
## Read-Only Transactions
While transactions are commonly used for modifying data, like with the account deposit example, they can also be used for read-only operations. A **read-only transaction** is useful for generating consistent reports or snapshots of data at a specific point in time. It prevents a user from seeing inconsistent data that might be in the middle of being changed by another concurrent transaction. This ensures that all data read within the transaction reflects the state of the database when the transaction began, regardless of any other ongoing changes.
## Implicit Transactions
It's important to note that a database is always in a transactional state. When you execute a single SQL query without explicitly beginning a transaction, the database implicitly starts a transaction for that single query and immediately commits it upon completion. Therefore, whether a transaction is user-defined or system-defined, all operations are handled within a transaction.

# Atomicity
**Atomicity** is a core property of relational, NoSQL, and other database systems. It ensures that a **transaction is treated as a single, indivisible unit of work**, much like a chemical atom. This means that all the queries within a transaction must succeed for the transaction to be considered complete. If even one query fails for any reason—such as an invalid syntax, a failed constraint, or a duplicate primary key—the entire transaction must be immediately rolled back. All changes made by the successful queries within that transaction are undone.
## Handling System Crashes
Atomicity also applies in the event of a system crash. If a database goes down in the middle of a transaction before it has been committed, all changes made by the transaction must be rolled back. When the database restarts, it must be able to detect the incomplete transaction and undo any changes that were written to the disk.

This is where database design trade-offs come into play. Some databases are "optimistic" and write changes to disk as they occur, assuming the transaction will eventually be committed. This makes the `COMMIT` operation very fast, but a `ROLLBACK` (or a crash recovery) can be very slow because it requires the database to go back and undo the changes on the disk. Other databases write all changes to memory first, and only write to disk during the `COMMIT`. This makes the `COMMIT` slower, but a `ROLLBACK` is extremely fast as it just involves clearing the memory.
## The Consequences of Lacking Atomicity
Without atomicity, data can become inconsistent. For example, in a money transfer scenario, if a transaction debits an account but a crash occurs before the other account can be credited, the money would be lost, and the data would be in a bad state. The first account would have a new, lower balance, but the second account's balance would remain unchanged. This is why long transactions are generally a bad idea. An atomic database must handle this cleanup process, ensuring that the data is returned to a consistent state, even if the database's startup is delayed while it performs this cleanup.

# Isolation
**Isolation** is a critical property that **deals with the potential for conflicts when multiple transactions run concurrently on the same data**. The core question isolation addresses is: can an in-flight transaction see the uncommitted or committed changes made by other transactions, whether those changes are uncommitted or already committed? The answer depends on the chosen isolation level, which determines how a database handles these concurrent operations.
### Undesirable Read Phenomena
When transactions are not properly isolated, they can lead to several undesirable **read phenomena**. These are problematic side effects that can cause data inconsistency.
- **Dirty Reads:** Occur when a transaction reads data that has been written by another transaction but not yet committed. If the other transaction then rolls back, the data read by the first transaction becomes invalid or "dirty."
- **Non-repeatable Reads:** Happen when a transaction reads the same data twice and gets a different value each time because another transaction committed a change in between the reads. This is particularly problematic for long-running transactions that need a consistent view of the data.
- **Phantom Reads:** This phenomenon occurs when a transaction reads a set of rows based on a search condition, and then a subsequent query in the same transaction returns a different number of rows because another transaction inserted or deleted rows that fit the search condition. This is different from a non-repeatable read because it involves a change in the number of rows, not just a change in a single row's value.
- **Lost Updates**: Occur when two transactions read and update the same data. The second transaction overwrites the changes of the first transaction, causing the first update to be lost.

## Isolation Levels
To solve these read phenomena, databases offer different **isolation levels**. These levels are a trade-off between consistency and performance. A higher level of isolation provides better data consistency but often comes with a performance cost.
- **Read Uncommitted:** This is the lowest isolation level. It allows a transaction to read uncommitted changes from other transactions, making it vulnerable to dirty reads and all other read phenomena. It is rarely used because of the high risk of data inconsistency.
- **Read Committed:** This is a very popular isolation level and the default for many databases. In this mode, a transaction only sees changes from other transactions once they are committed. While it prevents dirty reads, it is still susceptible to non-repeatable reads and phantom reads.
- **Repeatable Read:** This level ensures that a transaction can read the same row multiple times and always get the same value. It prevents dirty reads and non-repeatable reads. However, it does not prevent phantom reads, as new rows that were not initially read might still be inserted by other transactions.
- **Snapshot Isolation:** This level creates a "snapshot" of the database at the start of a transaction. The transaction then operates on this snapshot, seeing only the data that was committed at that time. This effectively eliminates all read phenomena (dirty, non-repeatable, and phantom reads) and is often used by databases like Postgres.
- **Serializable:** This is the highest and most strict isolation level. It ensures that concurrent transactions are executed in a way that produces the exact same result as if they had been run sequentially, one after the other. While it provides the highest level of data consistency, it can severely impact performance by limiting concurrency.

## Database Implementation of Isolation
Different database management systems (DBMS) implement isolation levels in various ways, using either a **pessimistic** or **optimistic** approach:
- **Pessimistic Concurrency Control:** This approach uses **locks** to prevent other transactions from accessing data that is being modified. When a transaction accesses a row, table, or page, it places a lock on it, ensuring that no one else can change it. While this guarantees consistency, it can lead to performance issues and lock escalations, where a large number of row locks can escalate into a full table lock.
- **Optimistic Concurrency Control:** This approach avoids locks, allowing transactions to proceed without waiting for others. Instead, conflicts are checked at `COMMIT` time. If a conflict is detected (i.e., another transaction has modified the same data), the database will fail the transaction, and the user must retry it. This approach is often faster as it avoids the overhead of managing locks, making it popular with many NoSQL databases.

# Consistency
**Consistency** is a key property that ensures the **data within a database remains in a valid state after any transaction**. A consistent state is defined by a set of rules and constraints that are pre-determined by the user. There are two types of consistency:
- **Consistency in Data:** This refers to the state of the data itself as it is stored on disk. It's defined by user-defined rules, such as **referential integrity**. This means that if one part of the data refers to another (e.g., a "like" entry referring to a "picture"), the relationship must be valid. For example, the number of likes on a picture should match the total count of likes in a separate tracking table, and a like should not exist for a picture that has been deleted (visual example in the next paragraph [Sources of Inconsistency](#Sources%20of%20Inconsistency)).
- **Consistency in Reads:** This applies to the system as a whole, especially in distributed systems. It means that after a change is committed, any subsequent read should immediately see that change. If a transaction writes a value to one database instance and a subsequent read from a different instance returns an old value, this is an inconsistency in reads.
## Sources of Inconsistency
Inconsistencies in data can arise from several sources:
- **Broken Atomicity:** If a transaction fails in the middle and is not properly rolled back, the data can be left in a corrupted state. For example, losing $100 after a crash during a transfer is a data inconsistency.
- **Lack of Isolation:** Insufficient isolation can lead to an inconsistent view of the data. For instance, a transaction might read a value and then a different one later on due to an update by another transaction.

The term **"eventual consistency"** is a concept often used in distributed systems. It means that while a read may not immediately reflect a recent write, the system will eventually become consistent once all updates have propagated. This applies only to consistency in reads, not to data corruption.

For data to become consistent in a distributed system, a process like **replication** is used. Changes made on a primary database are synced to replicas. If this process is asynchronous, there will be a delay, and a read from a replica might return an old value. This is a trade-off: asynchronous replication is faster but provides only eventual consistency, while **synchronous replication** is slower but guarantees strong consistency. This trade-off between speed and consistency is a major consideration in database design for both relational and NoSQL systems.

# Durability
**Durability** is the final property of ACID and ensures that once a transaction is successfully **committed**, its changes will persist permanently. This means that even in the event of a system crash or power loss, the committed data will not be lost and can be recovered when the system comes back online.

Databases achieve durability by writing changes to a non-volatile storage medium, such as a hard drive or SSD. This process is inherently slower than writing to volatile memory (RAM), so databases employ several techniques to balance performance with the guarantee of permanence.
## Durability Techniques
To balance performance with durability, databases use several key techniques:
- **Write-Ahead Logging (WAL):** To avoid the slow process of writing every change directly to the main data files and their associated indexes, databases first record a compressed log of the changes to a dedicated **Write-Ahead Log**. This log is small and fast to write to disk. This log acts as the source of truth; in the event of a crash, the database can use the WAL to reconstruct the state of the main data files, effectively "replaying" the committed changes. While the main data files are eventually updated, the immediate persistence of the WAL guarantees durability.
- **OS Cache Bypass:** When a database tells the operating system to write data to disk, the OS often temporarily stores it in its own memory cache to optimize performance by batching writes. The OS then tells the database the write was successful, even though it hasn't been written to the physical disk. This creates a risk of data loss if the system crashes before the cache is flushed. To prevent this, databases use a command like **`Fsync`** to force the OS to immediately write the data to the physical disk, bypassing the cache. This guarantees durability but is a slower operation.

Some databases, like Redis, offer options to sacrifice some durability for faster writes. For example, a user might choose to accept a slight risk of data loss in the event of a crash if their application's primary need is for high-speed writes and the data is not critical. This is a deliberate trade-off where durability is not fully guaranteed for the sake of performance.
