# Last Class (B+ Trees vs. Hash Tables)
Last class discussions highlighted hash tables as important data structures offering **O(1) average time complexity for lookups** (matching keys to values). Hash tables were presented with **static and dynamic hashing schemes**, capable of incrementally growing to accommodate more keys, with a primary focus on handling **conflicts** when different keys hash to the same location. Hash tables are predominantly used for **internal data structures** within database systems, such as page tables, page directories, or for managing the system's state. They are also utilised for efficient joins.

# Introduction to B+ Trees
This session shifts focus to **B+ trees**, which are presented as the **default choice for indexes in relational database systems**. If you execute a `CREATE INDEX` command, **99% of the time**, you will get a B+ tree implementation. The discussion will cover a high-level overview, basic design choices, and various optimisation techniques used in real-world systems today.

# B-Tree family
A B+ tree falls under the **category of B trees**, which can be a source of confusion in database literature. "B trees" can refer to the general class of data structures, a specific B tree structure, or even B+ trees as implemented in some systems (e.g., PostgreSQL refers to its B+ tree as a B tree).

There is **no single original paper for the B+ tree**; the one most commonly cited is from 1979 by IBM, which describes different variants, with the B+ tree being highlighted as most useful for database systems. The original authors, Bayer and McCreight, never explicitly defined what the "B" stands for, though common interpretations include "balanced," "broad," or "bushy." It could also be named after Bayer or Boeing, where the data structure was developed.

Several **B tree variants** exist:
• **B-link tree**: An idea from CMU in 1981 by Phil Lehman, which PostgreSQL's B tree implementation explicitly references.
• **B-Epsilon tree**: A type of **write-optimised B tree**.
• **BW tree**: A lock-free version out of Microsoft.

# Properties of a B+ Tree
A B+ tree is a **self-balanced, ordered tree** that supports searches, sequential access, insertions, and deletions, all with **logarithmic time complexity (log(N))**. This log(N) time corresponds to the **height of the tree**.

A key difference from generic binary search trees is that **nodes in a B+ tree can hold more than two keys**. This design choice is crucial for **minimising random I/O and maximising sequential I/O**. When a node is accessed, it essentially involves fetching a disk page, and by packing more keys into a page, fewer random disk accesses are needed to traverse the tree. The goal is to convert random I/O into sequential access, particularly when traversing down to the leaf nodes and then scanning along them to find data.

Formally, a B+ tree is an **M-way search tree** with the following properties:
* It is **perfectly balanced**: Every leaf node in the tree is at the same depth (same number of levels from the root). Some systems, like PostgreSQL, may slightly violate this for certain optimisations.
* **Node occupancy**: Every node, except the root, must be at least **half-full**. If a node can store 'M' keys, it must contain at least 'M/2' keys. Falling below this threshold typically triggers a merge operation.
* **Inner node pointers**: Every inner node with at least 'K' keys will have at least **K+1 non-null children** (pointers to nodes at the next level).

* **Inner nodes** (and the root) contain an **alternating pattern of pointers to other nodes and keys**. These keys act as "guide posts" or "traffic signs," dictating which path to follow down the tree. For example, a key of '20' in a root node indicates that keys less than '20' go left, and keys greater than or equal to '20' go right. In a database system, these pointers are typically **page IDs**.
* **Leaf nodes** store the **actual values associated with keys**. These values could be a **record ID** (e.g., page number and offset pointing to the tuple on disk) or, in some cases (like MySQL or SQLite), the **entire tuple data itself** (known as index-organised storage). Only primary key indexes should typically be index-organised to avoid data duplication.
* Crucially, B+ trees incorporate **sibling pointers at every level** (not just leaf nodes, as seen in B-link trees and PostgreSQL implementations). This allows for **efficient sequential scanning** along the leaf nodes once the correct starting point is found, without having to traverse back up the tree. This is particularly useful for range queries (e.g., "give me all keys greater than or equal to six"), as it minimises random I/O. Sibling pointers in inner nodes can also aid in splits and merges.

# Nodes
Within a node, keys and values are typically stored as **arrays of key-value pairs**. The keys are copies of the values from the indexed attributes in the table. Essentially, the **index is a sorted replica of a portion of the table**, providing fast, sorted access to data that might otherwise be unsorted. The database system automatically **maintains consistency** between the index and the table (e.g., inserts or updates to the table are reflected in the index).

The arrays within the nodes are usually kept in **sorted order**. **Null keys** are handled by placing them either at the beginning or end of the sorted order, which can be configurable in some systems based on query needs.

A significant design choice in B+ trees is the **absence of parent pointers** (pointers going back up the tree). This simplifies concurrency control and avoids potential deadlocks in multi-threaded environments, as operations don't need to acquire latches in two directions. Splits and merges in B+ trees do not rely on rotations, unlike AVL trees. The system manages the return path for operations like splits by keeping a **stack of visited nodes** as it traverses down the tree, along with their latches.

# B+ Tree Leaf Nodes
The **original B tree (from 1972)** stored all keys and their corresponding values (or pointers to data) throughout the entire tree structure, similar to an AVL tree. While this could be more space-efficient (as a key only appears once), it posed a significant problem for **sequential access**. To scan keys in order, a B tree would require traversing up and down the tree (a breadth-first search), which is very inefficient and requires holding latches on potentially large parts of the tree.

The **B+ tree design improves upon this by storing all actual data values (or record IDs pointing to them) exclusively in the leaf nodes**. Keys in inner nodes serve only as guide posts. This distinction offers two major advantages:

1. **Better concurrent access**: Once an operation reaches the leaf level, it no longer needs to hold latches on the upper levels of the tree, allowing other threads to perform operations on those upper parts concurrently.

2. **Maximised sequential I/O**: Because all values are in the leaf nodes, sequential scans can proceed efficiently by traversing along the linked leaf nodes without going back up, greatly reducing random disk access.

**Basic Operations: Insertions**

To insert a key into a B+ tree:

1. **Locate the correct leaf node**: Traverse the tree from the root, following the guide posts until the appropriate leaf node where the key should reside is found.

2. **Insert if space is available**: If the leaf node has sufficient space, the key-value pair is inserted in sorted order, and the operation is complete.

3. **Split if full**: If the leaf node is full, it must be **split into two new nodes**. The keys are divided, with roughly half going to each new node. The **middle key** from the divided set is then **copied up to the parent node** as a new guide post, along with a pointer to the newly created node.

4. **Recursive splitting**: If the parent node also becomes full due to the copied-up key, it too must split, and this process can **cascade all the way up to the root** of the tree.

**Basic Operations: Deletions**

To delete a key from a B+ tree:

1. **Locate and remove**: Traverse the tree to find the leaf node containing the entry to be removed. If the key is not found, no action is taken.

2. **Check occupancy**: After deletion, if the leaf node is still at least **half-full**, the operation is complete.

3. **Redistribution (Stealing)**: If the leaf node falls below the half-full threshold, the system first attempts to **redistribute keys with a sibling node** (a node at the same level). It tries to "steal" a key from a sibling, provided the sibling will not also fall below its minimum occupancy threshold. This may require a minor update to the guide post in the parent node.

4. **Merge**: If redistribution is not possible (e.g., all siblings are also at minimum occupancy), the node must **merge with one of its siblings**. Their contents are combined into a single node, and the corresponding guide post in the parent node is removed.

5. **Recursive merging**: Similar to splits, a merge can cause the parent node to fall below its minimum occupancy, leading to a **cascading merge process** that can go up to the root.

**Advanced Lookup Capabilities**

Unlike hash tables, which only support exact equality lookups (`key = value`) and require the entire key, B+ trees offer more flexible query capabilities due to their ordered nature.

• **Full Key Lookups**: Standard equality matching using all components of a composite key.

• **Prefix Search**: Queries can be performed using only the **leading part of a composite key** (e.g., searching for `A` and `B` in an index on `A, B, C` without specifying `C`). The system traverses the tree based on the available prefix and then scans along the leaf nodes for matches.

• **Suffix Lookup (Skip Scans)**: Some advanced systems (like Oracle and potentially SQL Server, but generally not PostgreSQL) can perform lookups even if only the **suffix of a composite key** is provided (e.g., searching for `B` and `C` without `A`). This is complex, potentially involving parallel traversal down multiple branches of the tree, and then combining results.

• **Query Optimiser Decisions**: The database's query optimiser determines whether to use an index or perform a full table scan based on factors like key statistics and the selectivity of the query. A sequential scan might be faster than multiple index probes if the optimiser determines the index isn't sufficiently helpful for the given query.

**Index Creation and Maintenance**

In most systems, the **programmer decides which indexes to create**. While there's ongoing research into automatic index selection, commercial tools (like SQL Server on Azure) can suggest indexes based on workload analysis. The decision involves a **trade-off**: indexes speed up read operations but add overhead to inserts, updates, and deletes (as they must be kept in sync with the table), and they consume additional storage and memory.

**Handling Duplicate Keys**

To maintain the log(N) performance guarantee with duplicate keys, B+ trees use two main approaches:

1. **Appending a Record ID (Most Common)**: A **hidden column or attribute**, typically the **record ID** (page number and offset of the actual tuple), is appended to the user-defined key within the index. This ensures that **every entry in the B+ tree is unique**, even if the user-defined key value is duplicated. For lookups, the system can still perform prefix searches on the user-defined key portion.

    ◦ Example: If a user inserts key '6' multiple times, the internal index key becomes `(6, RecordID1)`, `(6, RecordID2)`, etc., ensuring uniqueness.

2. **Overflow Leaf Nodes (Less Common, Generally Bad Idea)**: If a leaf node is full and a duplicate key is inserted, instead of splitting, an **overflow page** is created and linked to the main leaf node, forming a linked list of duplicate entries for that key.

    ◦ **Drawback**: This method **violates the log(N) guarantee** because scanning for a specific duplicate key might require traversing a sequential linked list of overflow pages. It also complicates splits and merges.

**Clustered Indexes**

Some database systems support **clustered indexes**, which dictate the **physical storage order of the actual table tuples on disk**.

• For example, in MySQL or SQLite, where leaf nodes of the primary key index _are_ the tuples themselves, it's inherently a clustered index. In systems like SQL Server or Oracle, you can explicitly define a table as `INDEX ORGANIZED` based on an index.

• **Advantage**: When data is physically sorted on disk according to the index, **sequential scans along the index's leaf nodes lead to sequential disk I/O for the actual data**, improving performance.

• **Non-clustered Indexes and Random I/O**: If an index is not clustered, scanning its leaf nodes might provide keys in sorted order, but fetching the actual tuples (via record IDs) could lead to **random disk I/O**, as the tuples themselves are not necessarily contiguous.

• **Optimisation for Non-Clustered Indexes**: To mitigate random I/O, a common strategy is to first perform the **index scan to collect all relevant record IDs**, then **sort these record IDs by their page ID**, and finally, retrieve the actual tuples from disk in this sorted page order. This converts random I/O for tuple retrieval into more sequential I/O, even if additional bookkeeping is needed to present results in the index's key order.

• **PostgreSQL's** **CLUSTER** **command**: PostgreSQL offers a `CLUSTER` command, which physically reorders the table on disk according to a specified index. However, this is a **one-time operation**; PostgreSQL **does not maintain this clustered order** as new data is inserted or modified, meaning the table can quickly become unsorted again.

**Key Design Choices and Optimisations**

Many design choices and optimisations for B+ trees are detailed in "Modern B-Tree Techniques" by Girth and Graefe, often referred to as "the Bible of B+ trees".

• **Node Size**:

    ◦ Typically, one node maps to one page in the database's buffer pool.

    ◦ **Configurable size**: Some systems allow custom page sizes for different tables/indexes.

    ◦ **Hardware dependency**:

        ▪ For **slower spinning disks**, larger page sizes (e.g., 1MB) are preferred to maximise sequential I/O.

        ▪ For **fast SSDs**, 8-10KB is generally considered optimal.

        ▪ For **in-memory databases**, 512 bytes is efficient, fitting within CPU cache lines.

• **Minimum Node Occupancy**: Some systems, like PostgreSQL (calling their B+ tree "non-balanced"), can temporarily violate the half-full rule to avoid premature merges if subsequent insertions are expected to fill the node.

• **Variable Length Keys**:

    ◦ **Avoiding direct key storage (Bad Idea)**: Storing only pointers (record IDs) to the actual keys in inner nodes can save space, especially for large keys. However, this is generally a **poor approach for disk-based systems** as it incurs significant **non-sequential I/O** overhead to fetch the actual key from disk for every comparison, while holding latches. This was briefly used in some 1980s in-memory databases (T-trees) but is not practical for modern systems.

    ◦ **Common approaches**: Using techniques like slotted pages or overflow pages within the node to manage variable-length data.

• **Key Search within a Node (Once in Memory)**:

    ◦ **Linear Scan**: Simplest, scanning keys one by one.

    ◦ **SIMD (Single Instruction, Multiple Data)**: Uses modern CPU vector instructions to perform parallel comparisons on multiple keys simultaneously, making linear scans much faster in batches.

    ◦ **Binary Search**: The **most common approach** for sorted keys, efficiently narrowing down the search space.

    ◦ **Interpolation Search**: The **fastest method** if keys are perfectly monotonic and without gaps (e.g., auto-incrementing primary keys), allowing direct calculation of the key's offset. However, this is rare in practice due to the strict data requirements.

• **Key Compression**: Leverages the sorted nature and shared domain of keys to reduce storage size:

    ◦ **Prefix Compression**: Identifies common prefixes among adjacent keys and stores the common prefix once, followed by only the unique suffixes.

    ◦ **Deduplication**: For non-unique keys (ignoring record IDs), the duplicate key is stored once, followed by a posting list of all corresponding values/record IDs. PostgreSQL 15 adopted this, significantly reducing node size.

    ◦ **Suffix Truncation (in inner nodes)**: Inner nodes only need to store the minimum prefix of a key necessary to differentiate between child pointers. This saves space but can complicate insertions if a new key falls within a truncated range.

• **Pointer Swizzling**:

    ◦ **Problem**: Pointers between B+ tree nodes are typically page IDs, requiring a lookup in the buffer pool's page table to get the actual memory address. This incurs overhead and potential random I/O if the page is not in memory.

    ◦ **Solution**: If a page is pinned in the buffer pool (meaning it won't be evicted), its page ID pointers to child pages can be **replaced with direct memory pointers** (swizzled).

    ◦ **Benefits**: Eliminates buffer pool lookups, resulting in **faster tree traversal**.

    ◦ **Caveats**: Swizzled pointers must be "unswizzled" back to page IDs before the page is flushed to disk. Pinned pages must remain pinned as long as other swizzled pointers point to them to prevent dangling pointers and memory errors.

• **Bulk Loading**: For efficient insertion of a large number of keys, the data is **presorted**, laid out as a set of leaf nodes with sibling pointers, and then the upper levels of the B+ tree (scaffolding) are built from the bottom up. This avoids the overhead of individual top-down insertions and frequent splits.

• **Write-Optimised B Trees (B-Epsilon Trees / Fractal Trees)**:

    ◦ **Motivation**: Standard B+ trees have expensive updates due to the need to maintain balance. Write-optimised variants aim to **delay updates**, accumulate them, and then apply them in batches to amortise the cost.

    ◦ **Mechanism**: Each root and inner node contains a **"mod log"**. New inserts and deletes are initially placed into this mod log, rather than immediately propagating down the tree.

    ◦ **Reads**: When a query searches for a key, it first checks the mod log at each node. If the key (or a pending deletion of it) is found in the mod log, the search might terminate early.

    ◦ **Mod Log Management**: When a mod log becomes full, its accumulated changes are "cascaded" down to the next level of nodes in a batch.

    ◦ **Read Performance**: While potentially making reads slower if mod logs become very large, this can be mitigated by using **Bloom filters** to quickly check for the presence of a key in the mod log.

    ◦ **Concept Connection**: This approach is conceptually similar to **log-structured storage**.

    ◦ **Examples**: Commercial implementations include TokuTech's "Fractal Trees" (for MySQL, now deprecated) and systems like SplinterDB and those used by Relational AI. This is an evolving area in database systems.

**PostgreSQL Demonstration**

A demonstration with a 27 million email address dataset illustrates the use of B+ tree and hash indexes in PostgreSQL.

• **EXPLAIN**: The `EXPLAIN` command in PostgreSQL provides insight into the query plan.

• **Index-Only Scan (Covering Index)**: PostgreSQL can perform an **index-only scan** if all the data required to answer a query can be found directly within the index (e.g., `SELECT MIN(email) FROM emails` where the index is on `email`). This avoids fetching the actual table tuples, even if record IDs are stored in the leaf nodes.

• **Sequential Scan vs. Index Scan**:

    ◦ For wildcard searches like `WHERE email LIKE 'a%'`, PostgreSQL often chooses a **sequential scan** even with a B+ tree index, especially if the `LIMIT` clause isn't fully optimised for in the query planner. Hash indexes **cannot be used for wildcard or range searches**.

    ◦ For range queries starting earlier in the alphabet (e.g., `WHERE email > 'Andy'`), a sequential scan might be chosen.

    ◦ For ranges towards the end (e.g., `WHERE email LIKE 'zzz%'`), an **index scan** is often chosen, as the system estimates that scanning from that point in the index would involve less data than a full table scan.

• **Hash Index Usage**: Hash indexes are used by PostgreSQL for **exact equality matches**, particularly with `IN` clauses or multiple `OR` conditions. For such queries, PostgreSQL performs multiple probes into the hash index, generates a bitmap of matching tuple IDs, and then combines (ORs) these bitmaps to identify the records to retrieve.

• **PostgreSQL** **CLUSTER** **Behaviour**: The `CLUSTER` command sorts the table physically according to a specified index. However, this sort order is **not maintained over time**. Subsequent inserts will place new tuples in arbitrary locations (e.g., a new tuple inserted after a `CLUSTER` operation might appear on page 299 instead of the first page), causing the table to become unsorted again.
