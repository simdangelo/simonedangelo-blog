## Introduction and Strategic Vision
The CI/CD pipeline represents the most engineered component of this entire infrastructure. I designed it as a **multi-account, multi-stage orchestration system** that enforces governance, enables traceability, and provides a clear separation between synthesis and deployment phases. The architecture follows AWS Well-Architected principles for operational excellence.

The fundamental design philosophy centers on **determinism and auditability**: every deployment can be traced back to a specific commit, every change can be previewed before execution, and the pipeline behavior is identical whether triggered automatically or manually.
## Multi-Account Deployment Model
### Account Topology
The deployment architecture spans **four AWS accounts** with distinct responsibilities:

| Account              | ID           | Purpose                                                   | Role               |
| -------------------- | ------------ | --------------------------------------------------------- | ------------------ |
| **advana** (central) | 656332797039 | Pipeline orchestration, code repository, artifact storage | Control plane      |
| **dev**              | 732789817868 | Development environment workloads                         | Target environment |
| **test**             | 643356557982 | Testing environment workloads                             | Target environment |
| **prod**             | 238788445602 | Production environment workloads                          | Target environment |

**Why this separation?** This model enforces the principle of least privilege at the account boundary level. The central "advana" account hosts CodePipeline and CodeBuild projects, but has no direct access to workload resources. To deploy, the pipeline must explicitly assume a cross-account role with scoped permissions. This creates a natural audit boundary and blast-radius limitation.
### Cross-Account Trust Architecture
The cross-account access is implemented through STS AssumeRole with the role name `advana-ca-codebuild-execution`. The trust relationship works as follows:
```
advana (656332797039)                    target account (dev/test/prod)
┌─────────────────────┐                  ┌─────────────────────────────┐
│   CodeBuild Role    │───AssumeRole────▶│  advana-ca-codebuild-       │
│                     │                  │  execution                  │
│ (Service Principal: │                  │                             │
│  codebuild.amazon-  │                  │ Trust: advana account       │
│  aws.com)           │                  │ Permissions: CDK deploy,    │
└─────────────────────┘                  │ ECR push, S3 access, etc.   │
                                         └─────────────────────────────┘
```

The helper function `do_assume_cross_account_role()` in codebuild-helpers.sh implements this:
```bash
do_assume_cross_account_role() {
    local _account_id=$1
    local _role_name=$2
    local _session_name="${PROJECT_NAME}-${BU}-${STAGE}-codebuild-role"
    
    CREDENTIALS=$(aws sts assume-role \
        --role-arn "arn:aws:iam::${_account_id}:role/${_role_name}" \
        --role-session-name "${_session_name}" \
        --query 'Credentials' \
        --output json)
    
    export AWS_ACCESS_KEY_ID=$(echo $CREDENTIALS | jq -r '.AccessKeyId')
    export AWS_SECRET_ACCESS_KEY=$(echo $CREDENTIALS | jq -r '.SecretAccessKey')
    export AWS_SESSION_TOKEN=$(echo $CREDENTIALS | jq -r '.SessionToken')
}
```

**Important detail for interviews:** The session name includes project name, business unit, and stage. This isn't just cosmetic—it appears in CloudTrail logs. When investigating "who changed what," we can trace back to exactly which pipeline execution made the change. This is a compliance requirement in enterprise environments.
## Pipeline Orchestration: CodePipeline Structure
### Pipeline Naming Convention
Pipelines follow a strict naming convention:
```
devops-{project_name}-{business_unit}-{stage}-v{major}-{minor}-{patch}
```

Example: `devops-cash-flow-simulator-mercato-PROD-v0-7-4`

**Why version in the pipeline name?** This approach solves the "which version is deployed" question instantly. You can look at the pipeline list in the AWS Console and immediately understand what version each environment has. It also enables parallel existence of multiple pipelines during migration periods.
### Two-Stage Pipeline Architecture
Each environment pipeline consists of two distinct stages:
```
CodePipeline: devops-cash-flow-simulator-mercato-{STAGE}-v{X-Y-Z}
┌──────────────────────────────────────────────────────────────────┐
│  Stage 1: Source                                                  │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │ Action: CodeCommit                                           │ │
│  │ Repository: devops-cash-flow-simulator                      │ │
│  │ Branch: v{X.Y.Z} (tag-based)                                │ │
│  │ Output: SourceArtifact                                      │ │
│  └─────────────────────────────────────────────────────────────┘ │
├──────────────────────────────────────────────────────────────────┤
│  Stage 2: Build                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │ Action Group A: Synth (buildspec-synth.yml)                 │ │
│  │ - CDK synthesize                                            │ │
│  │ - CDK diff (against current stack)                          │ │
│  │ - Commit diff file to repository                            │ │
│  │ - MANUAL APPROVAL REQUIRED                                  │ │
│  ├─────────────────────────────────────────────────────────────┤ │
│  │ Action Group B: Deploy (buildspec-deploy.yml)               │ │
│  │ - CDK deploy --require-approval=never                       │ │
│  │ - Uses synthesized templates from Synth stage               │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

**Why separate synth and deploy?** This separation provides a critical checkpoint. The synth stage generates a diff file showing exactly what will change, commits it to the repository, and then pauses for human approval. The operator can review the diff, verify the changes are expected, and only then approve the deployment. This prevents "surprise deployments" in production.
### AUTOSTART Configuration
The `parameter-devops-mercato.json` configuration defines per-environment automation behavior:
```json
{
  "codebuild": {
    "dev": {
      "AUTOSTART": "true"      // ← Pipeline triggers automatically on commit
    },
    "test": {
      "AUTOSTART": "false"     // ← Requires manual pipeline start
    },
    "prod": {
      "AUTOSTART": "false"     // ← Requires manual pipeline start
    }
  }
}
```

**Strategic reasoning:** Development environment benefits from continuous deployment—developers push code and see results immediately. However, test and production require explicit human intent to deploy. This isn't just a safety measure; it's a governance control ensuring deployments are deliberate business decisions, not accidental commits.
## BuildSpec Deep Dive
### The Synth BuildSpec (`buildspec-synth.yml`)
The synthesis buildspec has three phases with distinct responsibilities:
#### Install Phase
```yaml
phases:
  install:
    runtime-versions:
      python: $PYTHON_RUNTIME      # Retrieved from SSM (3.11)
      nodejs: $NODE_RUNTIME        # Retrieved from SSM (latest)
    commands:
      - source BUILD/codebuild-helpers.sh
      - do_check_environment_variables
      - do_login_code_artifact
      - do_install_dependencies
```

The install phase sets up the runtime environment. Notice the **runtime versions are parameterized**—they come from SSM Parameter Store, not hardcoded. This enables runtime upgrades without changing buildspecs.

The `do_login_code_artifact()` function authenticates against AWS CodeArtifact to pull private Python packages:
```bash
do_login_code_artifact() {
    local _domain="${CODE_ARTIFACT_DOMAIN}"
    local _domain_owner="${CODE_ARTIFACT_DOMAIN_OWNER}"
    local _repository="${CODE_ARTIFACT_REPOSITORY}"
    
    export CODEARTIFACT_AUTH_TOKEN=$(aws codeartifact get-authorization-token \
        --domain "${_domain}" \
        --domain-owner "${_domain_owner}" \
        --query authorizationToken \
        --output text)
    
    export CODEARTIFACT_PIP_URL="https://aws:${CODEARTIFACT_AUTH_TOKEN}@${_domain}-${_domain_owner}.d.codeartifact.eu-central-1.amazonaws.com/pypi/${_repository}/simple/"
}
```

**Interview point:** CodeArtifact authentication tokens expire after 12 hours. In long-running builds, you might need to refresh them. However, our builds complete in under 10 minutes typically, so this isn't a practical concern.
#### Pre-Build Phase
```yaml
pre_build:
  commands:
    - do_assume_cross_account_role $ACCOUNT_ID $CA_ROLE
```

This single line is deceptively simple but critical. Before any CDK operation, we assume the cross-account role in the target account. All subsequent AWS API calls use these temporary credentials.
#### Build Phase
```yaml
build:
  commands:
    - do_login_ecr
    - do_cdk_operation synth
    - do_cdk_operation diff
    - |
      git add Diff_files/cdk-diff-${BU}-${STAGE}.txt
      git commit -m "Auto-update CDK diff for ${BU}-${STAGE}"
      git push origin HEAD:$BRANCH_NAME
```

The build phase performs synthesis, generates the diff, and **commits the diff file back to the repository**. This is a key governance feature—the diff file is version-controlled, providing an audit trail of what was proposed for each deployment.
### The Deploy BuildSpec (`buildspec-deploy.yml`)
The deploy buildspec mirrors the synth structure but with key differences:
```yaml
build:
  commands:
    - do_login_ecr
    - export COMMIT_ID=${CODEBUILD_RESOLVED_SOURCE_VERSION}
    - do_cdk_operation deploy
```

**Critical detail:** The `COMMIT_ID` environment variable is set from `CODEBUILD_RESOLVED_SOURCE_VERSION`—this is the exact Git commit being deployed. This value propagates into the CDK context and ultimately into ECS task definitions as an environment variable. When you SSH into a container or check CloudWatch logs, you can see exactly which commit is running.
### The CDK Operation Function
The `do_cdk_operation()` function in `codebuild-helpers.sh` is the heart of infrastructure deployment:
```bash
do_cdk_operation() {
    local _operation=$1
    
    # Setup BuildKit for Docker operations (deploy only)
    if [[ "$_operation" == "deploy" ]]; then
        export DOCKER_BUILDKIT=1
        export BUILDKIT_PROGRESS=plain
    fi
    
    cd infra
    
    local _common_args=(
        "--context" "stage=${STAGE}"
        "--context" "business_unit=${BU}"
        "--context" "version_major=${VERSION_MAJOR}"
        "--context" "version_minor=${VERSION_MINOR}"
        "--context" "version_patch=${VERSION_PATCH}"
        "--context" "commit_id=${COMMIT_ID:-unknown}"
    )
    
    if [[ "$_operation" == "synth" ]]; then
        cdk synth "${_common_args[@]}" --all
    elif [[ "$_operation" == "diff" ]]; then
        cdk diff "${_common_args[@]}" --all > ../Diff_files/cdk-diff-${BU}-${STAGE}.txt 2>&1 || true
    elif [[ "$_operation" == "deploy" ]]; then
        cdk deploy "${_common_args[@]}" --all --require-approval=never
    fi
}
```

**Key observations:**
1. **Context injection:** All deployment parameters (stage, business unit, version) pass through CDK context. This makes the same codebase deployable to any environment simply by changing context values.
2. **BuildKit activation:** Docker BuildKit is only enabled for deploy operations. This enables advanced caching features (registry-based caching) that dramatically speed up container builds.
3. **Diff capture with `|| true`:** The diff command uses `|| true` because `cdk diff` returns a non-zero exit code when there are differences. Without this, the build would fail on any environment with pending changes.
4. **`--require-approval=never`:** In the deploy phase, we skip approval prompts because approval already happened at the pipeline level (between synth and deploy stages).
## Docker Build Optimization: BuildKit and Registry Caching
### The Caching Architecture
Container builds are often the slowest part of CI/CD pipelines. I implemented **registry-based BuildKit caching** to address this:
```
┌─────────────────────────────────────────────────────────────────────┐
│                       ECR Repository Structure                       │
├─────────────────────────────────────────────────────────────────────┤
│  cash-flow-simulator-frontend                                        │
│  ├── :latest          (deployed image)                              │
│  └── :cache           (BuildKit cache layers)                       │
│                                                                      │
│  cash-flow-simulator-simulation-ecs                                  │
│  ├── :latest          (deployed image)                              │
│  └── :cache           (BuildKit cache layers)                       │
│                                                                      │
│  cash-flow-simulator-simulation-lambda                               │
│  ├── :latest          (deployed image)                              │
│  └── :cache           (BuildKit cache layers)                       │
└─────────────────────────────────────────────────────────────────────┘
```

The CDK construct `AutoDeployingCachedECR` configures this:
```python
self.docker_image_asset = aws_ecr_assets.DockerImageAsset(
    # ... base configuration ...
    cache_from=[
        aws_ecr_assets.DockerCacheOption(
            type="registry",
            params={"ref": repo_tag_cache_url},  # :cache tag
        )
    ],
    cache_to=aws_ecr_assets.DockerCacheOption(
        type="registry",
        params={
            "mode": "max",             # Cache all layers, including intermediate
            "image-manifest": "true",  # ECR compatibility
            "oci-mediatypes": "true",  # ECR compatibility
            "ignore-error": "true",    # Don't fail on first build (no cache exists)
            "compression": "zstd",     # Fast compression
            "ref": repo_tag_cache_url,
        },
    ),
)
```

**Why registry caching over local caching?**
- **Local cache doesn't persist:** CodeBuild containers are ephemeral. Local Docker cache disappears after each build.
- **S3 cache is too slow:** Transferring gigabytes of cache layers to/from S3 can take longer than rebuilding.
- **Registry cache is optimal:** ECR is in the same region, layers are pulled on-demand (only what's needed), and the cache persists indefinitely.

**Performance impact:** Without caching, a full frontend build takes ~8 minutes. With registry caching, incremental builds (only code changes) complete in ~2 minutes.
### Multi-Stage Build Considerations
The `mode: "max"` parameter is critical for multi-stage Dockerfiles. Without it, BuildKit only caches the final stage layers. With `max` mode, all intermediate stages are cached, enabling efficient rebuilds when only later stages change.
## Local Development Parity: The infra.sh Script
The `infra.sh` script mirrors CI/CD behavior for local development:
```bash
#!/bin/bash

# Retrieve parameters from SSM
get_ssm_parameters() {
    PROJECT_NAME=$(aws ssm get-parameter --name "/devops/${PROJECT_NAME_BASE}/project_name" --query "Parameter.Value" --output text)
    CDK_VERSION=$(aws ssm get-parameter --name "/devops/${PROJECT_NAME_BASE}/${BU}/CDK_VERSION" --query "Parameter.Value" --output text)
    # ... additional parameters ...
}

# Main execution
case "$1" in
    --synth)
        do_assume_cross_account_role
        do_cdk_operation synth
        ;;
    --diff)
        do_assume_cross_account_role
        do_cdk_operation diff
        ;;
    --deploy)
        do_assume_cross_account_role
        do_cdk_operation deploy
        ;;
    --release)
        if [[ "$STAGE" == "dev" ]]; then
            echo "ERROR: Cannot release to dev environment via CodePipeline"
            exit 1
        fi
        trigger_codepipeline_release
        ;;
esac
```

**Key design principles:**
1. **Parameter retrieval from SSM:** Local script fetches the same parameters CodeBuild uses, ensuring consistency.
2. **Same cross-account pattern:** Local execution uses the same STS AssumeRole mechanism.
3. **Release safeguard:** The script explicitly prevents triggering CodePipeline for dev environment. Dev deployments should be direct (`--deploy`), while test/prod should go through the full pipeline (`--release`).

**Interview question: "Why not just run `cdk deploy` directly?"**

Answer: Running `cdk deploy` directly would:
- Skip the diff review process
- Miss CodeArtifact authentication for private packages
- Not set up proper cross-account credentials
- Not inject all required context variables
- Not benefit from registry caching

The infra.sh script encapsulates all this complexity into simple commands.
## Diff File Generation and Version Control Integration
### The Diff Workflow
The pipeline automatically generates and commits diff files to the repository:
```
Repository: devops-cash-flow-simulator
├── Diff_files/
│   ├── cdk-diff-automation.txt       # Automation/central account
│   ├── cdk-diff-MERCATO-PROD.txt     # Production diff
```

Here's an actual diff output from the production environment (from the file I read earlier):

```diff
Stack cash-flow-simulator-frontend-stack
[~] Custom::CDKECRDeployment ...CustomResource may be replaced
 └─ [~] SrcImage (may cause replacement)
     └─ [~] .Fn::Join:
```

**What this tells us:**

3. **Change correlation:** Diff file commit is linked to the code commit that triggered it

## Environment-Specific CDK Version Pinning

Notice the CDK versions differ per environment:

| Environment | CDK Version |
|-------------|-------------|
| dev | 2.143.1 |
| test | 2.149.0 |
| prod | 2.149.0 |

**Why version pinning?**

CDK releases frequently, and new versions occasionally introduce breaking changes or unexpected CloudFormation template differences. By pinning versions:

1. **Dev experiments first:** New CDK versions are tested in dev before promoting
2. **Consistent behavior:** Each environment behaves predictably
3. **Controlled upgrades:** Version upgrades are explicit decisions, not surprises

The `do_install_dependencies()` function respects this:

```bash
do_install_dependencies() {
    pip install aws-cdk-lib==${CDK_VERSION}
    pip install -r requirements.cdk.txt
    pip install -r requirements.txt
}
```

## Commit Traceability in Deployed Containers

One of the most valuable features for debugging is commit traceability. The `COMMIT_ID` flows through the entire pipeline:

```
CodeBuild                      CDK Context                    ECS Task Definition
┌──────────────────┐          ┌────────────────┐            ┌────────────────────┐
│ CODEBUILD_       │   ─▶     │ commit_id=     │     ─▶     │ Environment:       │
│ RESOLVED_SOURCE_ │          │ "ab0eaee..."   │            │ COMMIT_ID=         │
│ VERSION          │          │                │            │ "ab0eaee..."       │
└──────────────────┘          └────────────────┘            └────────────────────┘
```

In the diff file, you can see this in action:

```diff
[ ]   {
[ ]     "Name": "COMMIT_ID",
[-]     "Value": "ab0eaee18b79badfa0a25dee6108619aefa14c0e"
[+]     "Value": "unknown"
[ ]   }
```

The `-` line shows the previous commit; the `+` shows the new one (in this case "unknown" because the diff was generated locally without CODEBUILD_RESOLVED_SOURCE_VERSION).

**Practical usage:** When investigating a production issue, operators can:
1. Check the running container's COMMIT_ID
2. Find that exact commit in Git
3. Review what changed between last deployment and current

## CodeBuild Environment Configuration

### Compute and Timing

```json
{
  "BUILD_IMAGE": "aws/codebuild/amazonlinux2-x86_64-standard:5.0",
  "COMPUTE_TYPE": "BUILD_GENERAL1_MEDIUM",
  "TIMEOUT": 60
}
```

- **Image:** Amazon Linux 2 with standard toolchain (Python, Node.js, Docker pre-installed)
- **Compute:** MEDIUM provides 4 vCPUs and 7 GB RAM—sufficient for CDK synthesis and Docker builds
- **Timeout:** 60 minutes prevents runaway builds from consuming resources indefinitely

**Why MEDIUM over SMALL or LARGE?**

- SMALL (3 vCPUs, 3GB RAM): Docker builds run out of memory during pip installs
- MEDIUM (4 vCPUs, 7GB RAM): Adequate for parallel operations
- LARGE (8 vCPUs, 15GB RAM): Unnecessary cost increase with marginal speed improvement

## Error Handling and Resilience

### Graceful Diff Failures

```bash
cdk diff "${_common_args[@]}" --all > ../Diff_files/cdk-diff-${BU}-${STAGE}.txt 2>&1 || true
```

The `|| true` ensures the build continues even if diff fails. This handles:
- First deployment (nothing to diff against)
- Permission issues (caught later in deploy)
- Transient CloudFormation API errors

### Cache Initialization

```python
cache_to=aws_ecr_assets.DockerCacheOption(
    params={
        "ignore-error": "true",  # Don't fail on first build
    },
)
```

First builds have no cache to pull from. Without `ignore-error`, BuildKit would fail trying to pull non-existent cache layers.

## Security Considerations in CI/CD

### Credential Handling

1. **No long-lived credentials:** All access uses temporary STS credentials (maximum 1 hour)
2. **CodeArtifact tokens:** Expire after 12 hours, regenerated each build
3. **ECR authentication:** Token-based, no stored passwords

### Permission Boundaries

The cross-account role has scoped permissions:
- Can deploy CloudFormation stacks with specific naming patterns
- Can push to ECR repositories matching project name
- Cannot access resources from other projects
- Cannot modify IAM policies or create new roles

### Secrets Management

The `build_secrets` parameter in Docker builds:

```python
build_secrets={"CODEARTIFACT_PIP_URL": "env=CODEARTIFACT_PIP_URL"}
```

This passes CodeArtifact credentials as build secrets, not arguments. Build arguments appear in image layers; secrets do not. This prevents accidental credential exposure in pushed images.

## Summary: Why This Architecture

The CI/CD pipeline architecture reflects several key principles:

| Principle | Implementation |
|-----------|----------------|
| **Separation of concerns** | Synth vs Deploy stages, central vs target accounts |
| **Auditability** | Diff files in Git, session names in CloudTrail, COMMIT_ID in containers |
| **Governance** | Manual approval for test/prod, AUTOSTART control |
| **Consistency** | Local script mirrors CI/CD behavior exactly |
| **Performance** | Registry-based Docker caching, appropriate compute sizing |
| **Security** | Temporary credentials, scoped permissions, secrets management |
| **Flexibility** | SSM parameters enable runtime configuration changes |

This is the architecture I would defend in any interview—it's battle-tested, production-ready, and follows AWS best practices for enterprise deployments.
