## Why CDK Over Other IaC Tools
When we started this project, we had several options for defining infrastructure as code: Terraform, CloudFormation, Pulumi, and AWS CDK. Each has its strengths, and I've worked with all of them in various projects. For this particular system, we chose **AWS CDK with Python**, and the reasoning was quite deliberate.

The first consideration was **team expertise**. Our engineering team consists primarily of data engineers and data scientists who are deeply proficient in Python but have limited experience with HCL (Terraform's language) or YAML-heavy CloudFormation templates. CDK allowed us to define infrastructure using the same language we use for application code. When a data engineer needs to understand how the Lambda function they're calling is configured, they can read Python code rather than deciphering a 500-line CloudFormation template.

The second factor was abstraction capability. CDK excels at creating reusable constructs—higher-level abstractions that encapsulate multiple AWS resources into a single, configurable component. We have several custom constructs in this project, like `AutoDeployingCachedECR`, that would be much more complex to implement in pure CloudFormation. With CDK, we write a Python class, and it generates all the underlying resources.

Someone might ask: "Why not Terraform? It's more cloud-agnostic." That's true, but we're committed to AWS for the foreseeable future. The multi-cloud flexibility of Terraform wasn't a requirement, and it would have come at the cost of reduced AWS integration. CDK generates CloudFormation under the hood, which means we get native AWS support, stack drift detection, and seamless integration with other AWS services like Service Catalog or CloudFormation StackSets if we ever need them.
## Project Structure and Stack Organization
The infrastructure code lives entirely within the `infra` directory, completely separated from application code. This separation is intentional—it allows infrastructure changes to be reviewed, tested, and deployed independently of application releases when necessary.

The entry point is `app.py`, which instantiates the CDK application and creates all stacks:
```python
app = cdk.App()
account = os.environ["CDK_DEFAULT_ACCOUNT"]
region = os.environ["CDK_DEFAULT_REGION"]
project_name = app.node.try_get_context("project_name").replace("devops-", "")
stage = app.node.try_get_context("STAGE").lower()

for stack_name, stack_class in [
    ("athena", AthenaStack),
    ("frontend", FrontendStack),
    ("roles", RolesStack),
    ("shared", SharedResourcesStack),
    ("simulation-storage", SimulationStorageStack),
    ("simulation", SimulationStack),
    ("storage", StorageStack),
]:
    stacks[stack_name] = stack_class(
        app,
        construct_id=F"{project_name}-{stack_name}-stack",
        description=F"The stack containing '{stack_name}' resources for the project '{project_name}'.",
        env=env
    )
```

Why seven separate stacks instead of one monolithic stack? The answer involves deployment speed, blast radius, and logical organization.

**Deployment speed**: CloudFormation has limits on the number of resources per stack (500) and the rate at which it can process changes. By splitting resources across multiple stacks, we can deploy changes faster. When we modify only the Athena workgroup configuration, we don't need to wait for CloudFormation to evaluate every Lambda, ECS task, and S3 bucket in the project.

**Blast radius**: If a deployment fails, the blast radius is contained to a single stack. A problematic change to IAM roles won't roll back our storage configuration. This isolation makes debugging easier and reduces the risk of catastrophic failures.

**Logical organization**: Each stack corresponds to a functional domain. The `storage` stack manages data buckets. The `simulation` stack handles compute resources. The `roles` stack defines IAM policies. Engineers can quickly locate where specific resources are defined without searching through thousands of lines of code.
### Stack Dependencies
Not all stacks are independent. Some resources must exist before others can be created. We define these dependencies explicitly in app.py:
```python
stacks["frontend"].add_dependency(stacks["roles"])
stacks["simulation"].add_dependency(stacks["roles"])
stacks["simulation"].add_dependency(stacks["shared"])
```

The frontend stack needs IAM roles to exist before it can assign them to ECS tasks. The simulation stack needs both roles and shared resources (like the SNS failure topic) before it can configure Lambda failure destinations.

CDK respects these dependencies during deployment. If you run `cdk deploy --all`, it will deploy the roles stack first, wait for completion, then deploy frontend and simulation stacks in parallel. This ordering is automatic—we don't need to write complex deployment scripts or orchestration logic.
## The BaseStack Abstraction
Every stack in our project inherits from a custom `BaseStack` class defined in `base.py`. This class provides common functionality that every stack needs:
```python
class BaseStack(Stack):
    def __init__(self, scope: Construct, construct_id: str, **kwargs) -> None:
        super().__init__(scope, construct_id, **kwargs)
        self.project_name = self.node.try_get_context("project_name").replace("devops-", "")
        self.stage = self.node.try_get_context("STAGE").lower()
        self.wbs = self.node.try_get_context("WBS")
        self.business_unit = self.node.try_get_context("business_unit").lower()
        self.prefix = construct_id.replace("-stack", "").replace("-resources", "")
```

Why create a base class? Consider the alternative: every stack would need to independently parse context variables, look up VPCs, and resolve SSM parameters. By centralizing this logic in `BaseStack`, we ensure consistency and reduce code duplication.

The base class provides several utility methods that child stacks use frequently.

**SSM Parameter Lookup**: Instead of hardcoding resource ARNs, stacks look them up from SSM Parameter Store:
```python
def get_ssm_string_parameter(self, param_name: str) -> str:
    value = aws_ssm.StringParameter.from_string_parameter_name(
        scope=self,
        id=param_name[1:].replace("/", "-") + "-param-lookup",
        string_parameter_name=param_name
    )
    return value.string_value
```

**VPC and Security Group Lookups**: Since we deploy into existing VPCs managed by a central networking team, we need to look up these resources rather than create them:
```python
def lookup_vpc(self) -> aws_ec2.IVpc:
    vpc_id = self.node.try_get_context("VPC_ID")
    return aws_ec2.Vpc.from_lookup(self, id=F"{self.prefix}-vpc-lookup", vpc_id=vpc_id)
```

**Environment-Aware Role Resolution**: Different environments have different role names (dev roles vs. prod roles). The base class encapsulates this logic:
```python
def get_iren_ds_roles(self) -> List[aws_iam.ArnPrincipal]:
    match self.stage:
        case "dev":
            iren_ds_role_names = [
                "saml-adfs-iren-ds-dev",
                "AWSReservedSSO_ADVANA-DataScientist_d46169e107dc80cc",
            ]
        case "test":
            # Different roles for test environment
        case "prod":
            # Production-specific roles
    return [self.get_role(role_name) for role_name in iren_ds_role_names]
```

This pattern—using Python's `match` statement for environment-specific configuration—is much cleaner than the conditional logic you'd need in CloudFormation or Terraform.
## The AutoDeployingCachedECR Construct
The most sophisticated custom construct in our codebase is `AutoDeployingCachedECR`, defined in `ecr.py`. This construct demonstrates the power of CDK's abstraction capabilities.

The problem it solves is complex: we need to **build Docker images**, **push them to ECR**, and **ensure they're available before any Lambda or ECS task that references them is created**. This involves multiple AWS resources (ECR repository, IAM policies, Docker assets, ECR deployment) and careful dependency management.
### What the Construct Creates
When you instantiate `AutoDeployingCachedECR`, it creates:
1. **An ECR repository** with lifecycle rules to prevent unbounded image storage
2. **IAM policies** granting CDK's image publishing role permission to push images
3. **A Docker image asset** built using BuildKit with registry-based caching
4. **An ECR deployment** that copies the image from CDK's staging bucket to our repository

All of this happens through a simple instantiation:
```python
self.ecr = AutoDeployingCachedECR(
    self,
    id=F"{self.prefix}-ADCECR",
    ecr_repository_name=F"{self.prefix}",
    dockerfile=F"docker/frontend.dockerfile",
)
```
### Docker BuildKit Integration with Registry Caching
One of the most impactful optimizations in this construct is the use of BuildKit with registry-based caching. Traditional Docker builds are slow because they rebuild every layer from scratch. BuildKit can push and pull cache layers from a remote registry, dramatically speeding up builds when base layers haven't changed.
```python
self.docker_image_asset = aws_ecr_assets.DockerImageAsset(
    self,
    ...
    cache_from=[
        aws_ecr_assets.DockerCacheOption(
            type="registry",
            params={"ref": repo_tag_cache_url},
        )
    ],
    cache_to=aws_ecr_assets.DockerCacheOption(
        type="registry",
        params={
            "mode": "max",             # Support multi-stage builds
            "image-manifest": "true",  # ECR compatibility
            "oci-mediatypes": "true",  # ECR compatibility
            "ignore-error": "true",    # Don't fail on first run
            "compression": "zstd",
            "ref": repo_tag_cache_url,
        },
    ),
)
```

The `cache_to` configuration with `mode: max` is particularly important. Without this setting, BuildKit only caches the final stage of a multi-stage Dockerfile. With `mode: max`, it caches all intermediate stages, which is crucial for our Python images where the dependency installation stage takes the longest.

The `ignore-error: true` parameter handles a chicken-and-egg problem: on the very first deployment, there's no cache to pull from, which would cause the build to fail. This parameter tells BuildKit to proceed without cache if none exists.
### Dependency Chain Management
The construct carefully manages dependencies between resources. The Docker image can't be built until the ECR repository exists. The deployment can't happen until the image is built. These relationships are expressed through CDK's dependency API:
```python
def create_docker_image_deploy_and_dependency_chain(self) -> None:
    self.docker_image_asset.node.add_dependency(self.cdk_image_deploy_role)
    self.docker_image_asset.node.add_dependency(self.cdk_image_deploy_policy.policy_dependable)
    self.docker_image_asset.node.add_dependency(self.ecr_repository)
    self.docker_image_deploy = cdk_ecr_deployment.ECRDeployment(...)
    self.docker_image_deploy.node.add_dependency(self.docker_image_asset)
```
### Content-Based Cache Invalidation
CDK determines whether to rebuild Docker images based on content hashes. We augment this with custom hashing logic that includes the Dockerfile itself:
```python
extra_hash=hash_file_or_directory(os.path.join(self.dockerfile_directory, self.dockerfile)),
```

This ensures that changes to the Dockerfile trigger a rebuild, even if the application code hasn't changed.
## Context Variables and Configuration
CDK uses a concept called "context" to pass configuration values into the synthesis process. We use context extensively to make our stacks environment-aware without hardcoding values.

Context can come from multiple sources:
### Static Context in cdk.json
Some values are truly static and can be committed to the repository. The cdk.json file contains environment-specific endpoints and certificate ARNs:
```json
{
  "runner_api_endpoint": {
    "dev":  "https://8hpmmddo24-vpce-079c2b3b27e47102a.execute-api.eu-central-1.amazonaws.com/prod",
    "test": "https://8p44sish2j-vpce-0c13bb089617483ba.execute-api.eu-central-1.amazonaws.com/prod",
    "prod": "https://szejj20lf1-vpce-07be6bd15e2bbde66.execute-api.eu-central-1.amazonaws.com/prod"
  },
  "certificate_arn": {
    "dev": "arn:aws:acm:eu-central-1:732789817868:certificate/...",
    "test": "arn:aws:acm:eu-central-1:643356557982:certificate/...",
    "prod": "arn:aws:acm:eu-central-1:238788445602:certificate/..."
  }
}
```
### Cached Context in cdk.context.json
When CDK looks up existing resources (VPCs, security groups), it caches the results in cdk.context.json. This cache ensures deterministic deployments—if someone else created a new subnet, our deployment won't suddenly start using it unless we explicitly refresh the context.
```json
{
  "vpc-provider:account=732789817868:filter.vpc-id=vpc-04b3aa99e6fe8625d:region=eu-central-1:returnAsymmetricSubnets=true": {
    "vpcId": "vpc-04b3aa99e6fe8625d",
    "vpcCidrBlock": "10.224.12.0/22",
    "subnetGroups": [
      {
        "name": "Private",
        "type": "Private",
        "subnets": [...]
      }
    ]
  }
}
```

We commit this file to version control. Some teams prefer to gitignore it and regenerate during CI/CD, but we found that committing it provides better visibility into what resources CDK actually uses.

### Runtime Context from CLI

The most dynamic context comes from command-line arguments during synthesis and deployment. Looking at infra.sh, we pass numerous values:

```bash
cdk $CdkCommand $Stack                                \
    -c REGION=$Region                                 \
    -c project_name=devops-$ProjectName               \
    -c business_unit=${BusinessUnit^^}                \
    -c STAGE=${Stage^^}                               \
    -c TARGET_ACCOUNT=$AccountNumber                  \
    -c CODEARTIFACT_AUTH_TOKEN=${CodeArtifactToken}   \
    -c VPC_ID=$ProjectVPC                             \
    -c DEFAULT_SECURITY_GROUP_ID=$ProjectSG           \
    ...
```

This approach keeps sensitive values (like CodeArtifact tokens) out of version control while still making them available during synthesis.

## Removal Policies: A Conscious Safety Decision

Throughout the codebase, you'll notice deliberate choices about `RemovalPolicy`. This CDK concept determines what happens to resources when they're removed from the stack or the stack is deleted.

For **data buckets**, we use `RETAIN`:

```python
self.encrypted_bucket = EncryptedBucket(
    ...
    bucket_removal_policy=RemovalPolicy.RETAIN,
)
```

If someone accidentally deletes the storage stack, the bucket and its data remain. We'd rather deal with orphaned resources than lose production data.

For **query results and logs**, we use `DESTROY`:

```python
self.encrypted_bucket = EncryptedBucket(
    ...
    bucket_removal_policy=RemovalPolicy.DESTROY,
)
```

Query results are ephemeral—they can be regenerated by re-running queries. There's no value in retaining them if the stack is deleted.

For **DynamoDB tables**, we use `DESTROY` but with `deletion_protection=False`:

```python
self.dynamo_table = aws_dynamodb.Table(
    ...
    removal_policy=RemovalPolicy.DESTROY,
    deletion_protection=False,
)
```

This might seem risky, but our DynamoDB tables contain metadata, not primary data. The actual simulation results live in S3. If we lose the metadata, we can rebuild it from S3 contents.

## Cross-Stack References

When one stack needs to reference a resource from another stack, CDK provides built-in mechanisms for cross-stack references. However, we've chosen to use SSM Parameter Store instead:

```python
# In StorageStack
aws_ssm.StringParameter(
    self,
    id=F"{bucket_id}-param",
    string_value=self.encrypted_bucket.bucket.bucket_arn,
    parameter_name=F"/{self.project_name}/buckets/{scope}",
)

# In another stack
bucket_arn = self.get_ssm_string_parameter(F"/{self.project_name}/buckets/data")
```

Why this pattern instead of CDK's native cross-stack references? CDK cross-stack references create CloudFormation exports, which have limitations: you can't delete a stack if another stack imports its values. This can create deployment deadlocks.

With SSM parameters, stacks are loosely coupled. We can delete and recreate the storage stack without affecting consumers, as long as we recreate the SSM parameters with the same names. This flexibility is worth the small overhead of maintaining parameter names.

## Tagging Strategy

Every resource we create is tagged for cost allocation and ownership tracking. CDK makes this easy through tag propagation:

```python
cdk.Tags.of(stacks[stack_name]).add("WBS", wbs)
cdk.Tags.of(stacks[stack_name]).add("AdvanaProject", project_name)
```

The `Tags.of()` method applies tags to a construct and all its children. When we add a tag at the stack level, every resource in that stack—every bucket, every Lambda, every IAM role—inherits that tag.

The `WBS` tag is particularly important in our organization. It's a billing code that allows the finance team to attribute costs to specific projects. Without proper tagging, AWS costs become an undifferentiated mass that's impossible to analyze.

## Synthesized Output and CloudFormation

When you run `cdk synth`, CDK generates CloudFormation templates in the `cdk.out` directory. These templates are what actually gets deployed to AWS. Understanding this relationship is important for debugging.

If a deployment fails, the error messages come from CloudFormation, not CDK. You might see errors like "Resource X already exists" or "Circular dependency detected." To debug these, you often need to examine the generated CloudFormation template, not just your CDK code.

We've configured CDK to use the default bootstrap template, which creates a staging bucket for assets (Lambda code, Docker images) and IAM roles for deployment. The bootstrap resources are shared across all projects in an account, so we only bootstrap once per account.

## Third-Party CDK Libraries

We use several community-maintained CDK libraries that extend CDK's capabilities:

**`cdk-ecr-deployment`**: Provides the `ECRDeployment` construct that copies Docker images from CDK's staging location to our ECR repositories. Without this, we'd need to write custom Lambda functions or scripts to move images around.

**`aws-cdk.aws-glue-alpha`**: Provides higher-level constructs for Glue resources. The "alpha" designation means the API might change between versions, but the construct quality is mature enough for production use.

**`advanalib`**: Our internal library that provides constructs like `EncryptedBucket` (S3 bucket with KMS encryption) and `StreamlitHostingApplicationLoadBalancedFargateService` (a mouthful, but it sets up everything needed to run Streamlit on Fargate with an ALB).

The internal library is versioned and published to CodeArtifact. When we improve a shared construct, all projects benefit after updating their dependency version.

## Local Development vs. CI/CD Synthesis

The infrastructure can be synthesized and deployed from two locations: a developer's local machine (using infra.sh) or the CI/CD pipeline (using codebuild-helpers.sh).

Both paths use identical CDK commands with identical context values. The difference is how those values are obtained:

**Local development** reads SSM parameters from the central "advana" account and constructs context values dynamically:

```bash
AccountNumber=$(_get_ssm_param /GLOBAL/${BusinessUnit^^}/${Stage^^}/account)
ProjectVPC=$(_get_ssm_param /GLOBAL/${BusinessUnit^^}/${Stage^^}/vpc/default_vpc)
```

**CI/CD** receives these values through CodeBuild's parameter-store integration, which injects SSM parameters as environment variables:

```yaml
parameter-store:
  TARGET_ACCOUNT: "/GLOBAL/${BUSINESS_UNIT}/${STAGE}/account"
  VPC_ID: "/GLOBAL/${BUSINESS_UNIT}/${STAGE}/vpc/default_vpc"
```

This dual-path approach ensures that developers can test infrastructure changes locally before committing, while CI/CD maintains the authoritative deployment pipeline.

## Version Pinning Philosophy

We pin CDK and its dependencies to specific versions in requirements.cdk.txt:

```
aws-cdk-lib==2.143.1
cdk-ecr-deployment==4.0.1
```

Why strict pinning instead of ranges like `>=2.143.0,<3.0.0`? CDK releases frequently—sometimes multiple times per week—and breaking changes occasionally slip through. By pinning to exact versions, we ensure that builds are reproducible. A deployment today will use the same CDK version as a deployment next month.

Version updates are deliberate. When we want to upgrade CDK, we update the pin, test locally, verify in a dev environment, and then promote to production. This controlled approach has saved us from several CDK bugs that affected newer versions.
