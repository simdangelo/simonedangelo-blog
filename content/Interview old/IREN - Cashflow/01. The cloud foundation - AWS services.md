# The Cloud Foundation: AWS Services
## Introduction and Platform Choice
When we started designing this platform, the choice of **AWS** as our cloud provider was straightforward, but it was not arbitrary. The organization already had an established AWS footprint with mature governance, security policies, and networking infrastructure. We operate within a multi-account strategy managed at the enterprise level, which meant we could leverage existing VPCs, security groups, and identity federation without building everything from scratch.

The decision to stay within AWS rather than considering a multi-cloud approach was deliberate. We needed deep integration between compute, storage, and analytics services—something that becomes significantly more complex when spanning multiple providers. The latency between services, the authentication boundaries, and the operational overhead of managing multiple cloud consoles would have added complexity without providing tangible benefits for our use case.

We deploy exclusively in **eu-central-1** (Frankfurt), which is mandated by data residency requirements. All financial data must remain within the European Union, and Frankfurt provides the best latency for our primary user base in Northern Italy.
## Compute Layer: A Hybrid Approach with Lambda and Fargate
One of the most critical architectural decisions was how to handle compute workloads. We ended up with a dual-compute strategy:
- **AWS Lambda** for orchestration and short-lived tasks.
- **ECS Fargate** for heavy computational work.
### Why Lambda for Orchestration
The Lambda function we call "starter" serves a specific purpose: it receives a request from the frontend, validates the payload, prepares the execution environment, and spins up an ECS task. Someone might ask, "Why not just call ECS directly from the frontend?" The answer lies in abstraction and control. By placing a Lambda function between the user-facing application and ECS, we gain several advantages:
- First, we can perform validation and enrichment of the request before committing compute resources. If a user submits malformed parameters, we reject it immediately at the Lambda level without ever provisioning a Fargate task.
- Second, the Lambda gives us a consistent invocation interface—the frontend doesn't need to know about ECS networking, task definitions, or container overrides. It simply invokes a Lambda with a JSON payload.

Looking at the Lambda configuration in `simulation.py`, you'll see we provision it with 1024 MB of memory, a 15-minute timeout, and zero retry attempts. The memory allocation might seem generous for what is essentially an orchestrator, but Lambda allocates CPU proportionally to memory. With 1024 MB, we get enough CPU to quickly prepare the ECS task and handle the boto3 API calls without throttling. The zero-retry policy is intentional—if the task fails to start, we want to report that failure immediately rather than silently retrying and potentially creating duplicate jobs.
```python
self.lambdas[name] = aws_lambda.DockerImageFunction(
    ...
    timeout=Duration.minutes(15),
    memory_size=config["memory"],
    retry_attempts=config["retry"],
    on_failure=aws_lambda_destinations.SnsDestination(failure_topic),
    ...
)
```

The Lambda runs as a Docker container image rather than a ZIP deployment. This was a conscious choice because our simulation logic shares code with the ECS tasks. By using container images for both, we maintain a single build pipeline and guarantee that the Lambda and ECS environments have identical dependencies. If we had used ZIP-based Lambdas, we would have faced the challenge of managing two separate dependency trees.
### Why Fargate for Heavy Computation
The actual simulation workloads run on **ECS Fargate** with significant resource allocation: 8 vCPUs and 40 GB of memory. Why Fargate instead of EC2-backed ECS? The answer is operational simplicity and cost optimization.

With Fargate, we don't manage EC2 instances, AMIs, or capacity providers. We don't worry about patching, scaling policies, or instance right-sizing. We simply declare the resources we need, and AWS handles the rest. For workloads that are bursty and unpredictable—like simulation jobs triggered by users throughout the day—this on-demand model is more cost-effective than maintaining a fleet of EC2 instances that would sit idle most of the time.

The 8 vCPU / 40 GB configuration was determined empirically. Our simulations involve loading large Parquet datasets into memory, performing complex pandas operations, and writing results back to S3. We found that smaller configurations led to out-of-memory errors or unacceptably long execution times. The current sizing handles our largest datasets comfortably while remaining within Fargate's limits.
```python
num_vcpu = 8192 
memory_mib = 40960

fargate_task = aws_ecs.FargateTaskDefinition(
    self,
    id=F"{self.prefix}-default-task",
    cpu=num_vcpu,
    memory_limit_mib=memory_mib,
    runtime_platform=aws_ecs.RuntimePlatform(
        operating_system_family=aws_ecs.OperatingSystemFamily.LINUX,
        cpu_architecture=aws_ecs.CpuArchitecture.X86_64,
    ),
    ...
)
```

Why not use Lambda for everything, especially with Lambda's support for up to 10 GB of memory? The 15-minute execution limit is the primary constraint. Our simulations can run for 30 minutes or more depending on the dataset size and complexity. Fargate tasks have no such limit—they can run for hours if needed.
### The Frontend on Fargate
The web application runs as a **Streamlit service on Fargate**, fronted by an **Application Load Balancer**. The configuration is lighter than the simulation tasks: 2 vCPUs and 8 GB of memory. This sizing supports concurrent users while handling Streamlit's server-side rendering model, which keeps state in memory for each active session.

Why Fargate for the frontend instead of something like AWS App Runner or Elastic Beanstalk? We wanted full control over the networking configuration. The service runs inside a private VPC with no public IP assignment—all traffic flows through the ALB. This gives us TLS termination at the load balancer level using ACM certificates, and it integrates cleanly with our existing VPC endpoints for accessing other AWS services.
## Storage Architecture: S3 as the Data Lake Foundation
Our storage strategy centers on **Amazon S3**, which serves as the single source of truth for all persistent data. We maintain multiple buckets with distinct purposes:
1. **Data Bucket** (`{account}.cash-flow-simulator.data`): Stores input datasets, reference data, and configuration files. This bucket has versioning enabled because we need to track changes to input files over time.
2. **Simulations Bucket** (`{account}.cash-flow-simulator.simulations`): Stores simulation outputs, intermediate results, and extracted reports. Versioning is enabled only in production and test environments—not in dev, where rapid iteration makes versioning more of a hindrance than a help.
3. **Query Results Bucket** (`{account}.cash-flow-simulator.query-results`): Stores Athena query results temporarily. This bucket has a 7-day lifecycle policy that automatically deletes old results, keeping storage costs under control.

Looking at the storage stack in `storage.py`, every bucket is created using our custom `EncryptedBucket` construct, which wraps the standard S3 bucket with KMS encryption:
```python
self.encrypted_bucket = EncryptedBucket(
    self,
    id=bucket_id,
    bucket_name=bucket_name,
    key_name=kms_key_name,
    versioned=True,
    bucket_removal_policy=RemovalPolicy.RETAIN,
)
```

Why KMS-managed keys instead of S3-managed encryption (SSE-S3)? The answer lies in access control granularity. With KMS, we can grant or deny access to specific keys independently of bucket policies. If a role can access the bucket but not the KMS key, it cannot read the data. This provides an additional layer of defense-in-depth.

Each bucket has a corresponding SSM parameter that stores its ARN. This indirection allows other stacks and applications to reference buckets without hardcoding names. When a Lambda needs to read from S3, it looks up the bucket ARN from SSM Parameter Store, which we'll discuss in more detail later.
## Analytics Layer: Athena and Glue Data Catalog
For analytical queries over simulation results, we use **Amazon Athena** with the **AWS Glue Data Catalog** as the metastore. This combination gives us **serverless SQL capabilities without managing any infrastructure**.

The Athena workgroup configuration in `athena.py` reveals several important design decisions:
```python
self.workgroup = aws_athena.CfnWorkGroup(
    ...
    work_group_configuration=aws_athena.CfnWorkGroup.WorkGroupConfigurationProperty(
        bytes_scanned_cutoff_per_query=200_000_000_000,
        engine_version=aws_athena.CfnWorkGroup.EngineVersionProperty(
            selected_engine_version="Athena engine version 3"
        ),
        publish_cloud_watch_metrics_enabled=True,
        requester_pays_enabled=True,
        result_configuration=aws_athena.CfnWorkGroup.ResultConfigurationProperty(
            encryption_configuration=aws_athena.CfnWorkGroup.EncryptionConfigurationProperty(
                encryption_option="SSE_KMS", 
                kms_key=self.encrypted_bucket.kms_key.key_arn,
            ),
            output_location=self.encrypted_bucket.bucket.s3_url_for_object(),
        ),
    )
)
```

We explicitly pin to Athena engine version 3, which provides significantly better performance and supports newer SQL features compared to version 2. The 200 GB scan limit per query is a cost control mechanism—it prevents runaway queries from scanning terabytes of data and generating unexpected bills.

Why Athena instead of Redshift or another data warehouse? Our **query patterns** are **exploratory and ad-hoc**. Users run reports, investigate specific simulations, and export data subsets. We don't have the continuous, high-concurrency query load that would justify a provisioned data warehouse. Athena's **pay-per-query model** means we only pay when users actually run queries.

The data format on S3 is **Parquet with SNAPPY compression**. This columnar format dramatically reduces the amount of data Athena needs to scan, which directly reduces costs. When a user queries only three columns from a table with fifty columns, Athena reads only those three columns from disk.
## State Management: DynamoDB for Metadata
While S3 holds the actual data, **DynamoDB** serves as our **metadata store**. We maintain three tables:
- **simulation-runs**: Records each execution of a simulation, including status and timestamps  
- **jobs**: Tracks individual job executions within a simulation run

Why DynamoDB instead of a relational database like RDS PostgreSQL? Our access patterns are simple: we look up records by their unique ID, list records by user, and update status fields. These are classic **key-value operations** that DynamoDB handles efficiently with single-digit millisecond latency. We don't need complex joins, transactions across multiple tables, or sophisticated query capabilities.

The tables use provisioned capacity (5 read/write capacity units each) rather than on-demand pricing. This is a cost optimization—our metadata access is predictable and steady, so provisioned capacity is cheaper than on-demand. If we see throttling, we can increase the capacity or switch to on-demand.

Each DynamoDB table has its own customer-managed KMS key for encryption:
```python
self.dynamo_table_kms_key = aws_kms.Key(
    self,
    alias=kms_key_name,
    id=kms_key_name,
    enabled=True,
    enable_key_rotation=True,
    removal_policy=RemovalPolicy.DESTROY,
)
```

Key rotation is enabled, which means AWS automatically rotates the cryptographic material annually without any action required from us.
## Container Registry: ECR with Lifecycle Management
All our container images are stored in **Amazon ECR**. We maintain separate repositories for each image type:
- Frontend application
- Simulation Lambda
- Simulation ECS task

The ECR repositories are created with lifecycle policies that limit the number of images retained. This prevents unbounded growth as we deploy new versions. Without lifecycle policies, every deployment would leave behind old images, and storage costs would grow indefinitely.

The images are built using Docker BuildKit with registry-based caching. When we build a new image, Docker checks ECR for cached layers from previous builds. If the base layers haven't changed, they're pulled from the cache rather than rebuilt. This significantly speeds up deployment times, especially for our Python images where the dependency installation layer rarely changes.
## Messaging and Notifications: SNS for Failure Alerts
We use **Amazon SNS** for operational notifications. The primary use case is **failure alerts**—when a Lambda fails or an ECS task terminates abnormally, SNS sends email notifications to the engineering team.
```python
def create_failure_topic(self) -> None:
    topic = aws_sns.Topic(
        self,
        id=F"{self.project_name}-{topic_name}-topic",
        topic_name=F"{self.project_name}-{topic_name}",
    )
    for email_address in [
        "Enrico.Prampolini@gruppoiren.it",
        "Andrea.Schiappacasse@gruppoiren.it",
        "advanced_analytics@gruppoiren.it"
    ]:
        topic.add_subscription(aws_sns_subscriptions.EmailSubscription(email_address))
```

Why SNS instead of something like PagerDuty or Opsgenie directly? SNS serves as an abstraction layer. If we later decide to integrate with a different alerting system, we change the SNS subscription—not every Lambda configuration. Lambda supports SNS as a native failure destination, making the integration straightforward.
## Event-Driven Updates: EventBridge for Image Synchronization
One of our more sophisticated patterns involves **EventBridge** rules that detect ECR image pushes and automatically update Lambda functions. When a new image is pushed to the Lambda repository with the "latest" tag, an EventBridge rule triggers a helper Lambda that updates the simulation Lambda's underlying image.

```python
image_update_rule = aws_events.Rule(
    ...
    event_pattern=aws_events.EventPattern(
        source=["aws.ecr"],
        detail_type=["ECR Image Action"],
        detail={
            "action-type": ["PUSH"],
            "result": ["SUCCESS"],
            "repository-name": [repo.ecr_repository.repository_name],
            "image-tag": [config["ecr"]["tag"]],
        },
    ),
    targets=[
        aws_events_targets.LambdaFunction(
            image_updater_function,
            event=aws_events.RuleTargetInput.from_object({
                "name": F"simulation/{name}",
                "repository": repo.ecr_repository.repository_name,
                "tag": config["ecr"]["tag"],
            })
        )
    ],
)
```

This pattern decouples image building from Lambda deployment. We can build and push images without redeploying the entire stack—the EventBridge rule handles the Lambda update automatically.
## Configuration Management: SSM Parameter Store
We use AWS Systems Manager Parameter Store extensively as our configuration backbone. Every resource that other components need to reference is registered in SSM:
- Bucket ARNs: `/{project}/buckets/{scope}`
- KMS key ARNs: `/{project}/kms-keys/{scope}`
- Role ARNs: `/{project}/roles/{service}`
- Lambda function ARNs: `/{project}/lambdas/{category}/{name}`
- DynamoDB table names: `/{project}/dynamodb-tables/{scope}`
- Glue database names: `/{project}/glue-databases/{scope}`

This hierarchical naming convention makes it easy to understand what a parameter represents and to apply IAM policies that grant access to specific parameter paths.

Why SSM Parameter Store instead of environment variables or configuration files? Parameters can be updated without redeploying applications. If we need to point a service to a different bucket, we update the parameter value—the next time the service reads the parameter, it gets the new value. This is particularly useful for cross-stack references where one stack needs to know about resources created by another.
## TLS and Certificate Management: ACM
TLS certificates for the load balancer are managed through AWS Certificate Manager. We maintain separate certificates for each environment (dev, test, prod), referenced by ARN in the CDK context:
```json
"certificate_arn": {
    "dev": "arn:aws:acm:eu-central-1:732789817868:certificate/...",
    "test": "arn:aws:acm:eu-central-1:643356557982:certificate/...",
    "prod": "arn:aws:acm:eu-central-1:238788445602:certificate/..."
}
```

ACM handles certificate renewal automatically for certificates that are attached to AWS resources like ALBs. This eliminates the operational burden of tracking certificate expiration and performing manual renewals.
## Private Package Registry: CodeArtifact
Our Python applications depend on both public packages from PyPI and private packages developed in-house. AWS CodeArtifact serves as our private package repository, proxying requests to PyPI while also hosting our internal libraries.

During Docker builds, we inject the CodeArtifact URL as a secret so that pip can authenticate and pull packages:
```dockerfile
RUN --mount=type=secret,id=CODEARTIFACT_PIP_URL \
    python3.11 -m pip config set \
    global.index-url $(cat /run/secrets/CODEARTIFACT_PIP_URL)
```

This approach keeps credentials out of Docker build logs and image layers while enabling pip to resolve packages from our private registry.
## Summary of AWS Services
To summarize, here are all the AWS services that constitute our cloud foundation:

| Category | Services |
|----------|----------|
| **Compute** | Lambda, ECS Fargate |
| **Storage** | S3, DynamoDB |
| **Networking** | VPC, ALB, Security Groups |
| **Analytics** | Athena, Glue Data Catalog |
| **Container** | ECR |
| **Security** | KMS, IAM, ACM |
| **Configuration** | SSM Parameter Store |
| **Messaging** | SNS |
| **Events** | EventBridge |
| **Packages** | CodeArtifact |
| **Logging** | CloudWatch Logs |

Each service was chosen to fulfill a specific requirement while minimizing operational overhead. We favor serverless and managed services wherever possible—not because we can't manage servers, but because managing infrastructure is not our core competency. Our value lies in the simulation logic and analytics, not in patching operating systems or tuning database configurations.
