# Overview
AWS offers three primary compute paradigms:
1. Virtual machines via **Amazon EC2**
2. Serverless function execution via **AWS Lambda**
3. Container orchestration via **Amazon ECS** and **Amazon EKS**.

Each targets a different operational trade-off between control, flexibility, and management overhead.

# What Is a Server, and Why Does It Matter?
Before diving into AWS services, it's worth grounding the fundamental concept. A **server** is simply a computer that runs continuously, listening for and responding to requests from other computers (called **clients**). The word "server" describes a role, not a specific machine — your laptop can act as a server, and so can a $50,000 rack unit in a data center. What distinguishes production servers is that they are expected to be **highly available** (rarely or never offline), handle many concurrent clients, and be reachable over a network.

A **virtual machine (VM)** is a software-emulated computer that runs on top of a physical machine. Instead of buying dedicated hardware for every workload, a single physical server can host dozens of VMs, each with its own OS, CPU allocation, and memory. This is the foundational concept behind cloud computing: AWS owns the physical hardware, carves it into VMs, and rents those VMs to customers on demand.

# Amazon EC2
**Amazon Elastic Compute Cloud** (**EC2**) is AWS's VM rental service. You specify the hardware profile you need, and AWS provisions a virtual machine — called an **instance** — in one of its data centers, accessible over the internet.

EC2 instances run on one of two underlying models:
- **Bare-metal instances:** The customer gets an entire physical machine, undivided. No hypervisor sits between the application and the hardware. Used when workloads need direct access to CPU features like Intel VT-x (hardware-assisted virtualization), when regulations prohibit sharing physical hardware with other tenants, or when a custom hypervisor (e.g., Oracle) must be installed.
- **Hypervisor-based instances:** A **hypervisor** is a thin software layer that sits between the physical hardware and the VMs running on top of it. It allocates CPU time, memory, and I/O across multiple VMs simultaneously, each running its own OS in isolation. This is how AWS achieves multi-tenancy — many customers' VMs coexist on the same physical server without interfering with one another. AWS uses two hypervisors: the older **Xen** and the current **Nitro** system. Nitro offloads virtualization functions to dedicated hardware chips rather than software, which means the guest VM gets closer to bare-metal CPU and network performance, and the security boundary is enforced by hardware rather than software.
    

> **Note:** A single EC2 instance does not map one-to-one with a physical server. In the hypervisor model, multiple customers' instances share the same physical machine.
## Amazon Machine Image (AMI)
When you launch an EC2 instance, AWS needs to know what to put on it — which OS, which software, which configuration. That blueprint is called an **AMI (Amazon Machine Image)**. It is a snapshot of a fully configured system state, captured as a template that can be used to launch identical instances repeatedly and consistently.

The practical value is significant: instead of provisioning a raw VM and then running setup scripts to install dependencies, security agents, and application runtimes on every new instance, you bake all of that into a custom AMI once. Every instance launched from that AMI is guaranteed to start in the correct state — no missed steps, no configuration drift.

AMIs can be sourced from:
- **AWS-managed AMIs** (e.g., Amazon Linux 2 — free, fully supported by AWS)
- **AWS Marketplace** (third-party images, e.g., Red Hat, pre-hardened security images)
- **Custom AMIs** you build and maintain yourself

Key AMI selection factors:

|Factor|Detail|
|---|---|
|**Region**|AMIs are region-specific. To use one in a different region, you must copy it there first.|
|**OS and architecture**|Choose a 32-bit or 64-bit OS appropriate to your workload.|
|**Launch permissions**|AMIs can be public, shared with specific AWS accounts, or fully private.|
|**Root device storage**|AMIs are backed by either **Amazon EBS** or an **instance store**. EBS-backed instances boot in under one minute, support large volumes (up to 64 TB for io2 Block Express), and data persists independently of the instance's lifecycle. Instance store-backed instances boot in under five minutes, are capped at 10 GB, and lose all data when the instance stops or terminates. EBS is the default and strongly preferred choice for most workloads.|
## Instance Types
EC2 instance types define the hardware profile of a VM — CPU count, memory, local storage, and network bandwidth. AWS groups them into families based on what they are optimized for:

|Family|Representative Types|Best For|
|---|---|---|
|**General Purpose**|`m7i`, `t3`|Balanced CPU/memory/network; most typical web and app servers|
|**Compute Optimized**|`c7i`, `c6g`|CPU-bound workloads: HPC, batch processing, game servers|
|**Memory Optimized**|`r7g`, `x2idn`|Large in-memory datasets: caches, in-memory databases, real-time analytics|
|**Storage Optimized**|`i4i`, `d3`|High sequential I/O: data warehouses, Hadoop, distributed NoSQL|
|**Accelerated Computing**|`p4`, `g5`|GPU workloads: ML training/inference, video transcoding, computational finance|

When the right instance type isn't obvious upfront, start with a general-purpose instance, run load tests to find where performance degrades, and use those results to right-size.

Additional launch considerations:
- Attach a **key pair** at launch to enable SSH access to the instance.
- Instances are launched at the **Availability Zone (AZ) level**. Configure the VPC, subnet, security groups, and NACLs to control who can reach the instance and how.
- Assign a **public IP** if the instance needs to be directly reachable from the internet, subject to appropriate security group rules.
## Pricing Models

| Model                  | How It Works                                                                      | When to Use                                                      |
| ---------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **On-Demand**          | Pay per second, no commitment                                                     | Variable or unpredictable workloads, development environments    |
| **Reserved Instances** | 1- or 3-year commitment in exchange for up to 72% discount                        | Stable baseline capacity you know you'll need continuously       |
| **Spot Instances**     | Discounted access to unused EC2 capacity; AWS can reclaim with ~2 minutes' notice | Fault-tolerant, interruptible, or checkpoint-resumable workloads |

Spot instances represent idle capacity in AWS's data centers. AWS discounts this capacity to make use of it, but reclaims it when paying customers need it. They are well-suited for distributed batch jobs, large-scale ML training, and stateless processing pipelines where an occasional interruption is acceptable.
## Auto Scaling
Manually managing instance counts is impractical at scale. **Auto Scaling Groups (ASGs)** solve this by treating a fleet of EC2 instances as a managed pool that grows and shrinks automatically in response to demand.

Each ASG is configured with:
- A **minimum** and **maximum** instance count — hard bounds on fleet size
- A **desired capacity** — the current target the ASG actively maintains
- **Scaling policies** tied to CloudWatch metrics (e.g., CPU utilization, network I/O, or custom application metrics)
- A **cooldown period** (default: 300 seconds) — a mandatory pause after each scaling event before another is triggered, preventing rapid oscillation ("flapping")

**Example:** An ASG has a minimum of 1 and maximum of 4 instances, with a policy to add one instance when aggregate CPU exceeds 75% for five consecutive minutes. Once the threshold is breached, desired capacity increments and a new instance launches automatically — and scales back down when load subsides.

Beyond elasticity, ASGs provide **self-healing**: failed health check → the ASG terminates and replaces the instance automatically. Distributing an ASG across multiple AZs provides protection against AZ-level failures.

EC2 also supports **automatic instance recovery** at the individual level: if AWS detects a system-level hardware failure, it relaunches the instance on healthy hardware while preserving the same instance ID, metadata, attached EBS volumes, private IPs, and Elastic IPs.

> **Important caveat on spiky traffic:** Auto scaling is not instantaneous — new instances take time to boot, initialize the application, and pass health checks. For predictable traffic spikes (e.g., a scheduled event broadcast), **pre-scale proactively** before the spike arrives. For unpredictable spikes, set more aggressive thresholds (e.g., trigger at 60% CPU instead of 80%) to give the ASG more lead time. Keeping AMI images lean and startup dependencies minimal reduces the time-to-healthy for new instances.

# AWS Lambda
## What "Serverless" Actually Means
The term **serverless** is misleading — servers still exist and run your code. What serverless means is that **you, the developer, have no visibility into or responsibility for those servers.** AWS provisions, configures, patches, scales, and retires the underlying infrastructure entirely on your behalf. You provide only the code.

This is a meaningful shift in operational model. With EC2, you decide on instance types, manage OS patches, configure autoscaling, and pay for instances whether or not they are serving traffic. With a serverless model, you deploy code and pay only for the exact compute time consumed during execution. There is no idle cost, no capacity planning, and no OS-level maintenance.

The trade-off is reduced control. You cannot tune kernel parameters, choose a specific CPU model, or run processes that exceed the platform's constraints (e.g., Lambda's 15-minute execution cap). Serverless is a deliberate abstraction: it trades flexibility for simplicity and operational efficiency.
## Lambda Core Concepts
AWS Lambda is AWS's serverless compute service. You deploy a **Lambda function** — code in a supported runtime — and Lambda executes it in response to events, scaling the underlying infrastructure automatically.

**Function:** The unit of deployment. Code written in a supported language runtime (Node.js, Python, Java, Go, Ruby, .NET, and others) that implements specific logic and is invoked by a trigger.

**Trigger:** The event source that causes a function to execute. Examples: an HTTP request via API Gateway, an object upload to S3, a message arriving in an SQS queue, a scheduled CloudWatch Events rule, a record written to a DynamoDB Stream.

**Event:** A JSON document (or service-specific structured payload) passed to the function at invocation time. It carries the data the function needs to do its work — for example, an S3 event carries the bucket name and object key of the newly uploaded file.

**Execution environment:** A secure, isolated sandbox that Lambda provisions to run a function. Its characteristics are set by the function configuration:
- Memory: 128 MB to 10,240 MB. **CPU allocation scales proportionally to memory** — there is no separate CPU knob. If your function is CPU-bound, the lever to pull is memory.
- Maximum execution timeout: 15 minutes.
- Processor architecture: **ARM64** (AWS Graviton2, better price-performance) or **x86-64**.

**Deployment package:** Lambda receives function code as either:
- A **.zip archive** (max 250 MB unzipped) stored in S3. Lambda provides the OS and language runtime.
- A **container image** (max 10 GB) stored in Amazon ECR. The image must be OCI-compatible and must bundle the OS and runtime itself.

**Layers:** Shared libraries or utilities packaged separately and attached to multiple functions. Layers reduce per-function bundle size, speed deployments, and allow independent versioning of shared dependencies (e.g., a company-wide logging library used across 50 Lambda functions).

**Destination:** For asynchronous invocations, a downstream target that receives the invocation record on completion — either success or failure. Supported destinations: SQS, SNS, another Lambda function, or EventBridge. This is the serverless equivalent of a callback or a dead-letter queue pattern.
## Invocation Modes

|Mode|Triggered By|Behavior|Best For|
|---|---|---|---|
|**Synchronous**|API Gateway, ALB, AWS CLI/SDK|Caller blocks and waits for the response. Execution timeout up to 15 min (API Gateway caps at 29 seconds).|Request/response workloads requiring a real-time result|
|**Asynchronous**|S3, SNS, CloudWatch Events|Lambda queues the request, returns `202 Accepted` immediately to the caller. Supports automatic retries (up to 2) and configurable destinations.|Background processing, event fan-out, fire-and-forget tasks|
|**Polling**|SQS, DynamoDB Streams, Kinesis, Kafka|Lambda polls the source internally and invokes the function synchronously with a batch of records. AWS does not charge for polling; only function execution is billed. Retry behavior is governed by message/record expiration in the source (e.g., up to 14 days for SQS).|Stream and queue-based data processing pipelines|
## Cold Starts
Because Lambda provisions execution environments on demand, a function's first invocation (or any invocation that requires a new environment to be spun up — e.g., during a traffic spike) incurs a **cold start**: the time Lambda takes to allocate compute, pull the function code from S3 or ECR, initialize the language runtime, and execute any initialization code defined outside the main handler.

Cold start latency typically ranges from **100 ms to ~1 second** and, per AWS's own production analysis, affects roughly **1% of total invocations**. For many workloads this is acceptable. For latency-sensitive APIs, it can cause noticeable tail-latency spikes.

It's worth understanding the anatomy of a cold start:
1. Lambda allocates a compute slot and network resources
2. Function code is downloaded from S3 or ECR
3. The language runtime (e.g., JVM, Python interpreter) is initialized
4. Any code outside the main handler — global variables, SDK client initialization, database connection setup — is executed

Steps 1–3 are Lambda's overhead. Step 4 is the developer's contribution to cold start time, and it's the part you can directly control.

**Mitigation strategies:**
- **Execution environment reuse (warm starts):** Lambda retains a used execution environment for some time after a function completes, so the next invocation can reuse it without re-initialization. Developers can exploit this by issuing a scheduled "warming" invocation with dummy input before real traffic is expected. Only practical for scheduled or low-traffic functions — at scale, Lambda creates many concurrent environments regardless.
- **Provisioned Concurrency:** Pre-allocates a fixed number of fully initialized execution environments, always warm and ready to serve requests. A function with provisioned concurrency of 4 maintains 4 live environments at all times. This eliminates cold starts for those slots but incurs continuous cost even when no invocations occur.
- **Memory tuning:** Higher memory → more CPU → faster initialization and execution. Use the open-source [Lambda Power Tuning](https://github.com/alexcasalboni/aws-lambda-power-tuning) tool to empirically identify the memory setting that optimizes cost and performance for your specific function.
- **Minimize initialization code:** Every import and every SDK client you initialize at the global scope runs during a cold start. Import only what you need, and defer initialization of heavy resources where possible.
- **SnapStart (Java 11+):** Lambda snapshots the fully initialized execution environment's memory and disk state after the initialization phase. Subsequent cold starts restore from this cached snapshot rather than re-running initialization, dramatically reducing startup time for Java functions with heavy JVM and framework initialization.

# Containerization Services
## What Containers Are and Why They Matter
A **container** is a lightweight, self-contained unit of software that packages code together with all of its dependencies — runtime, libraries, configuration — into a single portable artifact. Unlike a VM, a container does not bundle a full OS; instead, it shares the host OS kernel, making containers significantly faster to start and more resource-efficient than VMs.

**Container orchestration** is the automated management of containers in production: deciding which host to place them on, restarting them if they crash, scaling them up and down, managing network routing between them, and performing rolling deployments. Doing this manually at scale is operationally untenable, which is why orchestration platforms exist.

AWS provides two managed container orchestration services: **Amazon ECS** (AWS's proprietary orchestrator) and **Amazon EKS** (managed Kubernetes).
## Amazon ECS
Amazon Elastic Container Service is AWS's fully managed container orchestration platform, deeply integrated with the rest of the AWS ecosystem. Let's the the core concepts.

**Task:** The atomic unit of deployment in ECS. A task runs one or more containers together (analogous to a Kubernetes pod). Containers within a task share network namespace and can communicate over localhost.

**Task Definition:** A versioned JSON configuration document specifying everything needed to run a task: container images, CPU and memory allocation, networking mode, IAM execution role, port mappings, environment variables, and volume mounts. Think of it as the "recipe" for a task.

**ECS Service:** Manages a desired count of running tasks. The service replaces failed tasks automatically, integrates with a load balancer to distribute traffic, and supports rolling deployments and autoscaling. It is the mechanism for keeping a long-running application alive.

**ECS Cluster:** A logical grouping of ECS services and tasks sharing underlying infrastructure. A single cluster can contain a mix of EC2 and Fargate launch types simultaneously.

**Amazon ECR (Elastic Container Registry):** AWS's managed Docker/OCI image registry. ECS pulls container images from ECR at task launch time. ECR integrates with IAM for access control and supports image vulnerability scanning.

**Example task definition (Fargate launch type):**
```json
{
  "family": "fargate-task-definition",
  "containerDefinitions": [
    {
      "name": "my-fargate-application",
      "image": "123456789.dkr.ecr.us-west-2.amazonaws.com/repository:tag",
      "portMappings": [{ "containerPort": 80, "hostPort": 80 }],
      "essential": true
    }
  ],
  "cpu": "256",
  "memory": "512",
  "networkMode": "awsvpc",
  "executionRoleArn": "arn:aws:iam::123456789:role/ecsTaskExecutionRole",
  "runtimePlatform": { "operatingSystemFamily": "LINUX" },
  "requiresCompatibilities": ["FARGATE"]
}
```

**ECS Launch Types:**

|Factor|ECS EC2|ECS Fargate|
|---|---|---|
|**Infrastructure management**|You manage instance type selection, fleet size, OS patching, and EC2 autoscaling|Fully serverless — AWS manages all underlying compute|
|**Pricing**|Charged for running EC2 instances + storage; no separate ECS fee|Charged per vCPU, memory, and storage consumed while tasks are active; no idle cost|
|**GPU support**|Yes|No|
|**Persistent storage**|EBS volumes supported|No EBS; use EFS for persistent shared storage, or bind mounts for ephemeral storage|
|**Best for**|High CPU/memory workloads, GPU requirements, compliance mandates, cost optimization at large scale|Batch workloads, small services with burst patterns, teams wanting zero infrastructure overhead|

ECS integrates natively with **CloudWatch** (metrics and logs), **IAM** (task-level permissions), **ALB** (traffic routing and health checking across tasks), and **AWS Cloud Map** (service discovery, allowing containers to find and communicate with each other by name).
## Amazon EKS
Amazon Elastic Kubernetes Service is a fully managed service that runs **Kubernetes** — the dominant open-source container orchestration system — on AWS.

**Kubernetes** manages clusters of machines running containers. Its architecture has two layers: the **control plane** (which makes scheduling decisions, maintains desired state, and exposes the Kubernetes API) and **worker nodes** (the machines that actually run containers). The control plane components include the **API server** (the entry point for all cluster operations) and **etcd** (a distributed key-value store that holds the entire cluster state). Managing these components reliably is operationally complex — EKS removes that burden by managing the control plane entirely on your behalf.

**Key EKS capabilities:**
- **Managed control plane:** EKS runs the Kubernetes API server and etcd across three AZs, with automatic detection and replacement of unhealthy control plane nodes. You pay a flat hourly fee for the control plane; you do not manage it.
- **Automated version upgrades:** EKS handles Kubernetes control plane version upgrades, keeping clusters on supported and patched versions without manual intervention.
- **Worker node flexibility:** Worker nodes can be EC2 instances — either self-managed, managed via EKS-managed node groups (which automate provisioning and lifecycle management), or Fargate pods for serverless container execution. EC2 node groups support ASGs, spot instances, and GPU-optimized instance types.
- **Hybrid deployments via AWS Outposts:** For workloads that must run on-premises due to latency or data residency requirements, EKS on Outposts extends AWS infrastructure into the customer's own data center, enabling Kubernetes workloads to run locally while remaining managed by the EKS service.
- **Ecosystem compatibility:** Because EKS runs standard upstream Kubernetes, it is compatible with the full CNCF ecosystem: Helm (package management), service meshes (Istio, Linkerd), GitOps tooling (ArgoCD, Flux), and the broader community of Kubernetes operators. This is a decisive advantage for teams with existing Kubernetes workflows or tooling investments.
- **Security and compliance:** Integrates with IAM for Kubernetes RBAC, VPC network policies for pod-level traffic control, and KMS for secret encryption at rest. Holds compliance certifications including SOC, PCI DSS, ISO, FedRAMP Moderate, and HIPAA.


**ECS vs. EKS — the practical distinction:** ECS is simpler and tightly AWS-native. If your team lives in the AWS console, uses AWS-native CI/CD, and doesn't need Kubernetes-specific features, ECS is lower overhead and faster to operate.

EKS is the right choice when your organization already runs Kubernetes, values workload portability across environments, needs Kubernetes-specific primitives (Custom Resource Definitions, admission controllers, operators), or wants to leverage the broader Kubernetes open-source ecosystem. The operational overhead of EKS is higher than ECS, but EKS on AWS offloads the hardest part — control plane management — entirely.

# Choosing a Compute Platform

|Dimension|EC2|Lambda|ECS Fargate|EKS|
|---|---|---|---|---|
|**Operational overhead**|High|Very low|Low|Medium|
|**Control / flexibility**|Maximum|Minimal|Moderate|High|
|**Scaling speed**|Moderate (ASG boot time)|Near-instant|Fast|Moderate|
|**Max execution duration**|Unlimited|15 minutes|Unlimited|Unlimited|
|**GPU support**|Yes|No|No (EC2 launch type only)|Yes (EC2 nodes)|
|**Cost model**|Per instance-hour|Per invocation + duration|Per vCPU/memory while active|Per node + control plane fee|
|**Best for**|Full hardware control, GPU, stateful apps, compliance|Event-driven, short-lived, burst workloads|Containerized apps without infra management|Kubernetes-native workloads, multi-cloud portability|

**Practical decision guidance:**
- Need full hardware control, persistent storage, or GPU? → **EC2** or **ECS EC2**
- Event-driven workloads, short execution windows, zero infra management? → **Lambda**
- Containerized apps, AWS-native tooling, no Kubernetes requirement? → **ECS Fargate**
- Existing Kubernetes investment, portability, or CNCF ecosystem needs? → **EKS**

No compute platform selection is permanent. Start with the option that fits your current team capability and traffic pattern, instrument it well, and re-evaluate as requirements evolve.
