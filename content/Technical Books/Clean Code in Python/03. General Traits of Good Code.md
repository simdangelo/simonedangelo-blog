This chapter and the next focus on higher-level software design principles applicable in Python. These principles serve as design tools for building quality software. Not all principles are always applicable; some represent different viewpoints (like Design by Contract vs. defensive programming) or depend on the context.
# Design by Contract
This section talks about how different parts of a software application interact with each other, especially when some code is meant to be used by other code, not directly by users. This interaction happens through **APIs (Application Programming Interfaces)**.

The code within these components works correctly only if certain conditions are met when it's called, and the calling code (the client) expects a specific result. If these expectations aren't met, it indicates a problem. For example, if a function needs integers as input but receives strings, it shouldn't just fail silently. Instead, it should clearly signal that it was called incorrectly.

While documentation can describe what inputs and outputs are expected, it can't automatically enforce these rules while the program is running. This is where **Design by Contract** comes in. The core idea of DbC is to make these expectations explicit through a **contract**. If this contract is broken, the code will raise an exception, clearly stating the reason. A contract mainly includes:
- **Preconditions**: These are checks performed **before** the code runs to ensure that all necessary conditions are met (e.g., validating input parameters). The caller is responsible for meeting these conditions.
- **Postconditions**: These are checks performed **after** the code has run to verify that the result is what the caller expected. The component providing the code is responsible for fulfilling these conditions.

Optionally, a contract can also include:
- **Invariants**: These describe things that should remain constant while the code is running.
- **Side effects**: These are any observable changes caused by the code.

While all these elements are part of the contract conceptually and should be documented, only **preconditions** and **postconditions** are usually enforced at the code level.

The main benefit of using DbC is that when errors happen, they are easier to find. By checking whether a precondition or a postcondition failed, you can quickly identify whether the problem lies with the code that called the function (client) or the function itself (supplier).

**Precondition checks** are especially important because if they fail, the code being called shouldn't run at all, as its basic requirements haven't been met. This helps to prevent further issues and clearly marks the responsibilities of different parts of the code.
## Preconditions
Preconditions are the guarantees that a function or method expects to receive to operate correctly. In programming, this often means providing well-formed data, like initialized objects and non-null values. In Python, due to its dynamic typing, this can also involve checking the specific type of data provided, beyond what static type checkers like mypy can do. A function should validate the data it receives before processing it.

This raises the question of where to put this validation. Should clients validate data before calling the function (a more tolerant approach where the function accepts potentially malformed data), or should the function itself validate everything it receives (a more demanding approach)? For Design by Contract (DbC), a demanding approach is generally preferred for robustness and is common practice.

Regardless of the chosen approach, the non-redundancy principle should be followed: each precondition should be enforced by either the client _or_ the function, but not both. This avoids duplicating validation logic, which also relates to the Don't Repeat Yourself (DRY) principle we'll discuss later.
## Postconditions
Postconditions are the part of the contract that checks the state _after_ a method or function has finished running and returned a result. Assuming the function was called correctly (meaning its preconditions were met), the postconditions guarantee that certain properties will hold true after execution. The purpose of postconditions is to verify and validate everything a client might expect from the function's outcome. If the method ran successfully and all postcondition checks pass, then the client should be able to use the returned object without issues, as the agreed-upon contract has been fulfilled.
## Pythonic contracts
Even though there isn't a built-in "Design by Contract" feature in Python (a proposal called PEP-316 was postponed), we can still use this design idea in our Python code.

The best way to do this is by adding checks within our methods, functions, and classes. If these checks fail (meaning a precondition or postcondition is not met), we should raise an exception like `RuntimeError` or `ValueError`. Choosing the right type of exception can depend on the specific situation. While `RuntimeError` and `ValueError` are common, you might need to create your own custom exception if they don't accurately describe the problem.

We also want to keep the code for preconditions, postconditions, and the main function logic separate. One way to do this is by creating smaller, focused functions. Another interesting approach, in some cases, is to use decorators.
## Design by contract – conclusions (Concise)
The key benefit of Design by Contract is precise error identification at runtime, clearly showing the broken code and violated contract. This makes code more robust as components enforce rules and maintain consistency, improving program correctness. Contracts also clarify program structure by explicitly stating function/method expectations and guarantees, replacing ad-hoc validations. While adding extra work (writing and potentially testing contracts), the improved quality is worthwhile for critical parts of the application. Focus on validating meaningful properties and conditions, not just data types (which tools like mypy handle better).
# Defensive Programming
Defensive programming is a way of writing code so that different parts of your program can protect themselves from bad or incorrect information they might receive. Instead of just defining rules that must be followed (like in Design by Contract), defensive programming focuses on making sure **each piece of code can handle unexpected inputs** without breaking down.

It's helpful to use defensive programming along with other good coding practices. It's not an either/or situation with Design by Contract; they can actually work well together.

The main ideas in defensive programming are:
- How to manage errors that you think might happen. This is called **error handling**.
- How to deal with errors that should never happen (impossible situations). This often involves using **assertions**.

We'll look at error handling and assertions in more detail later.
## Error handling
In our programs, we use **error handling** when we **expect that certain things might go wrong**, especially when dealing with input data.

The goal of error handling is to respond to these expected errors in a good way. We might try to keep the program running or decide to stop it if the error is too serious to fix.

There are different ways to handle errors, including:
- **Value substitution:** Replacing a bad input with a good default value.
- **Error logging:** Recording that an error happened.
- **Exception handling:** Using special mechanisms to deal with errors.

We will mainly focus on **value substitution** and **exception handling** because they offer more interesting ways to analyze how to manage errors. Error logging is also important, and we should always do it, but it's often used when there's not much else we can do. The other methods give us more options.
